# 원격 방 적용 설계 — 받은 것을 기기에 보이게 하기

## 문서 상태

- 작성일: 2026-08-31
- 작성: Claude Code
- 상태: **설계 / 구현 전 / 사용자 승인 대기**
- 선행 커밋: `26183c8` (복구 회전 + 실기기 양방향 shadow 복사)

이 문서는 다음 단계 하나를 정의한다. **받은 행을 기기에 실제로 보이게 하는 것.**
지금까지의 모든 복사는 단방향에 읽기 전용이었고 원본 대화 파일을 한 번도 쓰지
않았다. 이 단계는 처음으로 로컬에 쓴다. 승인 없이 구현하지 않는다.

---

## 1. 먼저 짚을 것 — "양방향"은 생각보다 좁다

canonical schema는 대화의 범위를 이렇게 정의한다.

```text
conversation_scope = (space_id, room_id, worldline_id?)
```

**대화는 공간이 소유한다.** 그리고 쓰기는 공간 경계가 걸린다. Worker의
`assertAuthenticatedWriteSpace`가 자기 공간 밖의 행 쓰기를 거부하고, 다른 공간을
대신 쓰는 delegated writer는 v1에 존재하지 않는다(Worker API 초안 §3).

그래서 v1에서 **한 대화를 두 기기가 함께 쓰는 일은 없다.** "양방향"의 실제 뜻은
이것뿐이다.

| 것 | v1 |
| --- | --- |
| 각 기기가 자기 공간의 행을 쓴다 | ✅ 이미 구현·검증됨 |
| 모든 기기가 모든 공간의 행을 받는다 | ✅ 이미 구현·검증됨 (change feed는 계정 단위) |
| 받은 방을 화면에 보이게 한다 | ⬜ **이 문서의 범위** |
| 다른 기기가 소유한 방에 이어 쓴다 | ❌ v1 범위 밖 (delegated writer 계약 없음) |

결정 6번("기존 방 이어가기만 허용")은 원격 탭의 **새 방 생성 금지**를 뜻하며,
다른 공간에 쓰는 권한을 주는 것이 아니다. 이어 쓰기까지 열려면 delegated writer
계약이 먼저 필요하고 그것은 별도 작업이다.

이 구분이 중요한 이유는 다음 절에 있다.

---

## 2. 이 설계의 핵심 — 사용자 대화 파일을 병합하지 않는다

앞 단계 보고에서 "처음으로 로컬 대화 파일에 써넣게 되므로 위험하다"고 적었다.
그 우려의 큰 부분은 §1 때문에 사라진다.

받는 기기 입장에서 원격 방은 **자기가 소유하지 않은 공간의 방**이다. 그 방의
로컬 파일은 애초에 존재하지 않는다. 따라서 **기존 대화에 병합할 일이 없고**,
새 파일을 만들 뿐이다.

규칙으로 못박는다.

> **적용 대상은 이 기기가 소유하지 않은 공간의 방뿐이다.**
> 자기 공간의 방은 자기가 진실의 원본이므로, 원격에서 받은 자기 행은 **읽고
> 대조만 하고 절대 적용하지 않는다.**

이 규칙 하나가 "사용자 대화가 원격 자료로 덮어써진다"는 사고 유형을 통째로
막는다. 병합 알고리즘이 없으면 병합 버그도 없다.

구현에서 이 규칙이 지켜지는지 확인하는 방법은 소유 공간 판정 한 곳뿐이다.

```text
apply(row) 는 row.identity.space_id != 이 기기의 registered_space_id 일 때만 수행
```

## 3. 원격 방은 어디에 저장하는가

두 안을 검토했다.

**안 A — 기존 방 저장소에 넣고 원격 표시를 붙인다.**
`rooms_list.json`과 `room_<id>_messages.json`을 그대로 쓰고 방에 출처 표시를
더한다. 화면 코드가 거의 그대로 동작한다는 장점이 있다.

문제는 **같은 파일 공간을 공유한다**는 것이다. 원격 적용에 결함이 생기면 그
결함이 사용자 자기 대화가 들어 있는 디렉터리와 같은 색인·같은 저장 스케줄러를
건드린다. `ChatStore.saveMessages`는 목록 전체를 다시 쓰고, 검색 색인을 다시
만들고, 방 미리보기와 `lastMessageTime`을 갱신한다. 원격 방 하나 때문에 사용자
방 목록의 정렬이 바뀌는 것은 사소하지만, 같은 경로를 공유한다는 사실 자체가
"자기 방은 절대 안 건드린다"를 코드로 증명하기 어렵게 만든다.

**안 B — 별도 원격 저장소를 두고 화면에서 합친다. (채택)**
원격 방은 `sync/remote/` 아래 자기 파일에 저장한다. 기존 `ChatStore`의 파일,
검색 색인, 저장 스케줄러를 **전혀 건드리지 않는다.** 채팅 목록 화면에서만 두
목록을 합쳐 보여준다.

채택 이유는 안전성이다. 원격 적용 코드가 사용자 대화 파일에 접근할 **경로 자체가
없다.** 잘못 짜도 사용자 대화를 못 건드린다. 이번 작업에서 나온 결함 셋이 전부
"조용히 틀린 채 화면상 정상"이었던 점을 감안하면, 신뢰를 코드 리뷰가 아니라
구조로 확보하는 편이 낫다.

대가는 화면 코드가 두 출처를 합쳐야 한다는 것이다. 이건 어차피 필요하다 —
결정 7번이 채팅 탭에 출처 표시를 요구한다.

## 4. 무엇을 보여주는가 — 노출 규칙

제품 결정이 이미 정해 두었다. 코드가 이를 어겨서는 안 된다.

| 원격 방의 공간 | Mac | Android 폰 | Android 태블릿 |
| --- | --- | --- | --- |
| `PHONE_SPACE` | **숨김** (결정 3) | 자기 것 | **숨김** (결정 3) |
| `MAC_SPACE` | 자기 것 | 보임 | **숨김** (결정 5) |
| `TABLET_SPACE` | 보임 | 보임 | 자기 것 |

결정 3은 폰 방을 다른 기기에서 숨기고, 결정 5는 Mac 방을 태블릿에서 초기에
숨긴다. 결정 9(하트 비공유)는 결정 3이 이미 자동으로 달성한다 — 하트는
`PHONE_SPACE` 안에만 있고 그 공간이 숨겨지기 때문이다.

**주의.** 이 표대로면 이번에 실기기로 확인한 폰 방 "역방향테스트"는 Mac 화면에
**보이면 안 된다.** 그 확인은 복호화 가능 여부를 증명한 것이지 표시를 승인한 것이
아니다. 백업은 되고 표시는 안 되는 것이 결정 3의 내용이다.

따라서 **표시까지 실제로 확인할 수 있는 조합은 하나뿐이다: Mac 방 → 폰.**
첫 적용 시험은 이 방향으로 한다.

## 5. 원격 방은 읽기 전용이다

결정 15번이 첫 테스트에서 수정·삭제를 막는다. §1에 따라 이어 쓰기도 v1에 없다.
따라서 원격 방은 v1에서 **완전한 읽기 전용**이다.

화면에서 입력창을 숨기는 것으로 끝내지 않는다. 원격 저장소에는 애초에 쓰기 API를
두지 않는다. 입력창을 숨기는 것은 UI 결정이고, 쓰기 API가 없는 것은 구조적
사실이다. 결정 8번(지원하지 않는 방의 안내)은 이 읽기 전용 상태를 방 진입 시
1회 알리는 것으로 만족시킨다.

## 6. 적용 절차

pull은 이미 있다. 새로 필요한 것은 replica에서 방을 조립하는 단계다.

1. **pull** — 기존 `SyncPullCoordinator`가 bootstrap과 changes를 replica에 넣는다.
   변경 없음.
2. **선별** — replica에서 이 기기가 소유하지 않은 공간의 행만 고른다(§2).
   노출 규칙(§4)에 걸리는 공간은 여기서 버린다.
3. **복호화** — 행이 적힌 공간으로 scope key를 유도해 연다. 이미 검증된 경로다
   (`SyncShadowVerifier`, `SyncShadowReader`).
4. **조립** — 방·turn·말풍선을 `bubble_order`로 정렬해 원격 저장소에 쓴다.
5. **대조** — 조립 결과의 개수와 내용 hash를 쓴 기기가 보고한 값과 비교한다.
   불일치는 조용히 넘어가지 않고 화면에 남긴다.

4단계는 **원자적 교체**로 한다. 방 하나의 파일을 임시 파일에 다 쓰고 rename한다.
부분 적용된 방은 사용자에게 "대화가 잘렸다"로 보이고, 그것은 결함이 아니라
데이터 손실처럼 읽힌다.

## 7. 이번 작업에서 배운 것 — 계속 의심할 것

세 결함 모두 **화면상 정상으로 보였다.**

| 결함 | 증상 | 왜 안 보였나 |
| --- | --- | --- |
| 합류 전 account id | 복호화 0/N | 신원·순서·hash는 account와 무관 |
| `_enc` 접미사 | 복호화 0/N | 봉인 필드 없음과 빈 행이 구분 안 됨 |
| `worldline_key` | 없음 (우연히) | 이번 행에 worldline이 없어서 맞았음 |

적용 단계에서 같은 종류가 나올 자리를 미리 적어 둔다.

- **wire 이름을 손으로 적는 모든 곳.** fixture를 손수 만들면 잘못된 가정이
  양쪽에 똑같이 들어가 사이좋게 통과한다. fixture는 실제 writer가 뽑고, Worker
  시험이 실제 change feed와 대조한다. 이번에 이미 그렇게 바꿨고 유지한다.
- **개수만 맞고 내용이 틀린 경우.** 개수 대조는 통과하는데 순서가 뒤집혔거나
  다른 방 행이 섞였을 수 있다. 내용 hash가 이걸 잡는다. **개수 일치만으로
  성공을 보고하지 않는다.**
- **부분 복호화.** N개 중 일부만 열렸는데 "받았다"고 표시하면 사용자는 잘린
  대화를 정상으로 믿는다. 전부 열리지 않으면 방을 적용하지 않는다.
- **worldline 있는 방.** 방 제목은 null-worldline scope, 말풍선은 worldline
  scope다. 폰 단톡방을 적용할 때 처음으로 실제로 걸린다. 다만 §4에 따라 폰 방은
  어차피 표시하지 않으므로 v1 적용 대상이 아니다.

## 8. 단계별 gate

각 단계는 앞 단계가 통과한 뒤에만 시작한다.

- [ ] **G1 — 조립기와 원격 저장소.** 합성 fixture로 선별·복호화·조립·원자적
      교체를 검증한다. 실기기 없음, 실데이터 없음.
- [ ] **G2 — 소유 공간 불변식.** 자기 공간 행이 적용되지 않는 것을 시험으로
      고정한다. 자기 공간 행을 섞은 replica로 확인한다.
- [ ] **G3 — 노출 규칙.** §4 표의 아홉 칸을 각각 시험으로 고정한다.
      특히 폰 방이 Mac·태블릿에서 걸러지는 것.
- [ ] **G4 — 실기기 적용.** Mac 방 "테스트2"를 폰에 적용한다. 개수·hash 대조와
      전부 복호화 확인. **사용자 승인 필요.**
- [ ] **G5 — 화면 표시.** 채팅 목록에 출처 표시와 함께 나타나고 읽기 전용으로
      열린다. 결정 8번의 1회 안내.
- [ ] **G6 — 범위 확대.** 방 하나가 성공한 뒤에만 다른 방을 연다.

## 9. 이 문서가 승인하지 않는 것

- 다른 공간의 방에 이어 쓰기 (delegated writer 계약 없음)
- 폰 방을 Mac·태블릿에 표시 (결정 3)
- Mac 방을 태블릿에 표시 (결정 5)
- 원격 방의 수정·삭제 (결정 15)
- 첨부 복사 (아직 경로 없음, 미복사 개수만 보고)
- 자동 동기화 켜기 — 모든 적용은 여전히 버튼 뒤에 둔다
- OS 알림 (결정 14)
