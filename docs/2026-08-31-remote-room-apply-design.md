# 원격 방 적용 설계 — 받은 것을 기기에 보이게 하기

## 문서 상태

- 작성일: 2026-08-31
- 작성: Claude Code
- 상태: **설계 / 구현 전 / 사용자 승인 대기**
- 선행 커밋: `26183c8` (복구 회전 + 실기기 양방향 shadow 복사)

이 문서는 다음 단계 하나를 정의한다. **받은 행을 기기에 실제로 보이게 하는 것.**
지금까지의 모든 복사는 단방향에 읽기 전용이었고 원본 대화 파일을 한 번도 쓰지
않았다. 이 단계는 처음으로 로컬에 쓴다. 승인 없이 구현하지 않는다.

## 1. 먼저 짚을 것 — 대화는 공간이 소유한다

canonical schema는 대화의 범위를 이렇게 정의한다.

```text
conversation_scope = (space_id, room_id, worldline_id?)
```

**대화는 공간이 소유한다.** 그리고 쓰기는 공간 경계가 걸린다. Worker의
`assertAuthenticatedWriteSpace`가 자기 공간 밖의 행 쓰기를 거부하고, 다른 공간을
대신 쓰는 delegated writer는 v1에 존재하지 않는다(Worker API 초안 §3).

| 것 | v1 |
| --- | --- |
| 각 기기가 자기 공간의 행을 쓴다 | ✅ 이미 구현·검증됨 |
| 모든 기기가 모든 공간의 행을 받는다 | ✅ 이미 구현·검증됨 (change feed는 계정 단위) |
| 받은 방을 화면에 보이게 한다 | ⬜ **이 문서의 범위** |
| 받은 방에 이어 쓴다 (결정 6) | ⬜ **이 문서의 범위** — §1.1의 방식으로 |

### 1.1 이어가기는 "자기 공간에 쓰고 합쳐서 보여주기"다

**2026-08-31 사용자 결정.** 초안은 이어가기를 "delegated writer가 없으므로 v1
범위 밖"이라 적고 원격 방을 읽기 전용으로 고정했다. 이것은 잘못이었다. 결정
6번은 이어가기를 허용하고, 결정 8번 각주는 **읽기 전용이 검토자 권고였고 사용자가
그것과 다른 선택을 했다**고 명시한다. 기술 제약을 근거로 제품 결정을 바꿀 수 없다.
제약은 "무엇을 할 수 없다"가 아니라 "어떻게 해야 하는가"의 문제였다.

채택한 방식은 이렇다.

> **답장은 답하는 기기가 자기 공간에 같은 `room_id`로 쓴다.**
> 한 방의 대화는 여러 공간에 걸친 행들의 **합집합**이며, 화면에서 시각 기준으로
> 정렬해 하나의 대화로 보여준다.

그 합집합의 canonical handle은 `(origin_space_id, room_id)`이다. 원래 방을 만든
공간은 `origin_space_id`, 각 행을 실제로 쓴 공간은 `space_id`로 보존한다. 허용되는
writer shard는 다음 세 줄뿐이다.

| origin | 허용 writer shard |
| --- | --- |
| `PHONE_SPACE` | `PHONE_SPACE` |
| `MAC_SPACE` | `MAC_SPACE`, `PHONE_SPACE` |
| `TABLET_SPACE` | `TABLET_SPACE`, `MAC_SPACE`, `PHONE_SPACE` |

기존 protocol v1 writer가 `origin_space_id`를 생략하면 Worker는 `target.space_id`로
정규화하고 origin shard만 생성하게 한다. 이어쓰기 shard는 원래 방의 origin을
명시해야 하며, projection은 항상 정규화된 값을 내보낸다.

폰이 Mac 방 `R`에 답하면 그 말풍선은 `(PHONE_SPACE, R)`에 적힌다. Mac의 원래
말풍선은 `(MAC_SPACE, R)`에 그대로 있다. 두 기기 모두 두 공간의 행을 받으므로
같은 대화를 본다.

이 방식을 고른 이유.

- Worker의 공간 쓰기 경계를 **그대로 지킨다.** 이미 구현돼 있고 시험으로 고정돼
  있으며, 한 기기가 망가져도 다른 공간을 건드리지 못하는 격리가 유지된다.
- 누가 썼는지가 행의 `space_id`에 남는다. 출처 표시(결정 7)가 자연히 따라온다.
- delegated writer 계약과 그에 딸린 인증·권한 설계를 만들지 않아도 된다.

**대가와 그에 따르는 필수 작업.**

- `bubble_order`는 `(account, space, room, worldline)` 단위다. 따라서 **공간을
  가로지르는 전체 순서를 보장하지 않는다.** 화면 정렬은 말풍선 평문 metadata의
  `timestamp`를 기준으로 하고, 같은 시각이면 `(space_id, bubble_order)`로 안정
  정렬한다. 이 규칙을 §6.5로 못박는다.
- 같은 `room_id`가 여러 공간에 존재하는 것이 **정상 상황이 된다.** §3.1의 저장
  identity와 §7의 코드 수정이 여기서 필수가 된다.
- 시계가 어긋난 기기끼리는 순서가 어긋날 수 있다. v1은 이를 감수하고, 어긋남이
  실제로 문제가 되면 별도 순서 계약을 만든다.

이 구분이 중요한 이유는 다음 절에 있다.

## 2. 이 설계의 핵심 — 사용자 대화 파일을 병합하지 않는다

앞 단계 보고에서 "처음으로 로컬 대화 파일에 써넣게 되므로 위험하다"고 적었다.
그 우려의 큰 부분은 §1 때문에 사라진다.

받는 기기 입장에서 원격 방은 **자기가 소유하지 않은 공간의 방**이다. 그 방의
로컬 파일은 애초에 존재하지 않는다. 따라서 **기존 대화에 병합할 일이 없고**,
새 파일을 만들 뿐이다.

규칙으로 못박는다.

> **적용 대상은 이 기기가 소유하지 않은 공간의 방뿐이다.**
> 자기 공간의 방은 자기가 진실의 원본이므로, 원격에서 받은 자기 행은 **읽고
> 대조만 하고 절대 적용하지 않는다.**

이 규칙 하나가 "사용자 대화가 원격 자료로 덮어써진다"는 사고 유형을 통째로
막는다. 병합 알고리즘이 없으면 병합 버그도 없다.

구현에서 이 규칙이 지켜지는지 확인하는 방법은 소유 공간 판정 한 곳뿐이다.

```text
apply(row) 는 row.identity.space_id != 이 기기의 registered_space_id 일 때만 수행
```

## 3. 원격 방은 어디에 저장하는가

두 안을 검토했다.

**안 A — 기존 방 저장소에 넣고 원격 표시를 붙인다.**
`rooms_list.json`과 `room_<id>_messages.json`을 그대로 쓰고 방에 출처 표시를
더한다. 화면 코드가 거의 그대로 동작한다는 장점이 있다.

문제는 **같은 파일 공간을 공유한다**는 것이다. 원격 적용에 결함이 생기면 그
결함이 사용자 자기 대화가 들어 있는 디렉터리와 같은 색인·같은 저장 스케줄러를
건드린다. `ChatStore.saveMessages`는 목록 전체를 다시 쓰고, 검색 색인을 다시
만들고, 방 미리보기와 `lastMessageTime`을 갱신한다. 원격 방 하나 때문에 사용자
방 목록의 정렬이 바뀌는 것은 사소하지만, 같은 경로를 공유한다는 사실 자체가
"자기 방은 절대 안 건드린다"를 코드로 증명하기 어렵게 만든다.

**안 B — 별도 원격 저장소를 두고 화면에서 합친다. (채택)**
원격 방은 `sync/remote/` 아래 자기 파일에 저장한다. 기존 `ChatStore`의 파일,
검색 색인, 저장 스케줄러를 **전혀 건드리지 않는다.** 채팅 목록 화면에서만 두
목록을 합쳐 보여준다.

채택 이유는 안전성이다. 원격 적용 코드가 사용자 대화 파일에 접근할 **경로 자체가
없다.** 잘못 짜도 사용자 대화를 못 건드린다. 이번 작업에서 나온 결함 셋이 전부
"조용히 틀린 채 화면상 정상"이었던 점을 감안하면, 신뢰를 코드 리뷰가 아니라
구조로 확보하는 편이 낫다.

대가는 화면 코드가 두 출처를 합쳐야 한다는 것이다. 이건 어차피 필요하다 —
결정 7번이 채팅 탭에 출처 표시를 요구한다.

### 3.1 저장 identity — `room_id`만으로 식별하지 않는다

canonical scope가 `(space_id, room_id, worldline_id?)`이므로 원격 저장소의 저장·
조회·원자적 교체 단위도 같아야 한다. §1.1의 이어가기를 열면 **같은 `room_id`가
여러 공간에 존재하는 것이 정상**이 되므로 이것은 선택이 아니다.

| 대상 | 저장 단위 |
| --- | --- |
| 방 메타(제목 등) | `(space_id, room_id)` |
| turn·말풍선 파일 | `(space_id, room_id, worldline_key)` — null worldline은 `''` |
| 원자적 교체 | 위 단위 하나씩 |
| 개수·내용 hash | 위 단위 하나씩 계산한다 |

화면에 보이는 "한 방"은 같은 `(origin_space_id, room_id)`를 가진 여러 저장 단위의 합집합이며,
합치는 일은 화면 계층에서만 한다. 저장 계층은 공간을 절대 합치지 않는다.

**G1·G2 fixture에 같은 `room_id`가 서로 다른 공간에 있는 경우를 반드시 넣는다.**
지금 코드가 이 경우를 틀리게 다루기 때문이다(§7.1).

## 4. 무엇을 보여주는가 — 노출 규칙

제품 결정이 이미 정해 두었다. 코드가 이를 어겨서는 안 된다.

| 원격 방의 공간 | Mac | Android 폰 | Android 태블릿 |
| --- | --- | --- | --- |
| `PHONE_SPACE` | **숨김** (결정 3) | 자기 것 | **숨김** (결정 3) |
| `MAC_SPACE` | 자기 것 | 보임 | **숨김** (결정 5) |
| `TABLET_SPACE` | 보임 | 보임 | 자기 것 |

결정 3은 폰 방을 다른 기기에서 숨기고, 결정 5는 Mac 방을 태블릿에서 초기에
숨긴다. 결정 9(하트 비공유)는 결정 3이 이미 자동으로 달성한다 — 하트는
`PHONE_SPACE` 안에만 있고 그 공간이 숨겨지기 때문이다.

**주의.** 이 표대로면 이번에 실기기로 확인한 폰 방 "역방향테스트"는 Mac 화면에
**보이면 안 된다.** 그 확인은 복호화 가능 여부를 증명한 것이지 표시를 승인한 것이
아니다. 백업은 되고 표시는 안 되는 것이 결정 3의 내용이다.

따라서 **표시까지 실제로 확인할 수 있는 조합은 하나뿐이다: Mac 방 → 폰.**
첫 적용 시험은 이 방향으로 한다.

## 5. 원격 방에 무엇을 할 수 있는가

읽기 전용이 **아니다.** 초안의 오류를 §1.1에서 바로잡았다.

| 행위 | v1 | 근거 |
| --- | --- | --- |
| 읽기 | ✅ | — |
| 이어서 답하기 | ✅ 자기 공간에 쓴다 | 결정 6, 8 |
| 새 방 만들기 | ❌ | 결정 6 ("새 방 생성" 금지) |
| 수정·삭제 | ❌ 첫 테스트에서 막는다 | 결정 15 |
| 다른 공간의 행을 고치기 | ❌ 구조적으로 불가 | Worker 공간 경계 |

**원격 저장소 자체는 읽기 전용으로 둔다.** 이것은 사용자 권한 이야기가 아니라
저장 계층의 성질이다. 사용자가 답을 쓰면 그 말풍선은 원격 저장소가 아니라 **이
기기의 자기 공간 outbox로** 나가고, 서버를 거쳐 다시 원격 저장소로 들어온다.
로컬에서 원격 저장소를 직접 고치는 경로는 만들지 않는다.

이렇게 하면 §2의 불변식이 답장을 열어도 그대로 유지된다. 원격 저장소에 쓰는 것은
"pull한 것을 조립하는 코드" 하나뿐이다.

결정 8번(지원하지 않는 방의 안내)은 **답변 방식의 차이**를 알리는 것으로
만족시킨다. 예: 폰 단톡방 기능이 없는 Mac에서 그 방에 답하면 개인방처럼 답한다는
안내. "읽기만 가능하다"는 안내가 아니다.

### 5.1 아직 정해지지 않은 것

이어가기를 실제로 구현할 때 다음이 더 필요하다. **이 문서는 방식만 정했고
아래는 열려 있다.**

- 답장이 어느 `turn_id`에 붙는가. 새 turn을 만드는 것이 자연스럽지만, 원격 turn을
  이어받는 경우의 규칙을 정해야 한다.
- 답장한 방의 `bubble_order`는 자기 공간에서 0부터 시작한다. 화면 정렬(§6.5)이
  이를 감춰야 한다.
- AI 응답을 어느 기기가 생성하는가. 답을 쓴 기기가 생성하는 것이 자연스럽지만,
  모드·모델·압축 설정이 기기마다 다르므로(결정 12) 별도 확인이 필요하다.

이것들은 G5 이후 별도 gate로 다룬다. **G1~G4는 표시와 적용만 다룬다.**

## 6. 적용 절차

pull은 이미 있다. 새로 필요한 것은 replica에서 방을 조립하는 단계다.

1. **pull** — 기존 `SyncPullCoordinator`가 bootstrap과 changes를 replica에 넣는다.
   변경 없음.
2. **선별** — replica에서 이 기기가 소유하지 않은 공간의 행만 고른다(§2).
   노출 규칙(§4)에 걸리는 공간은 여기서 버린다.
3. **복호화** — 행이 적힌 공간으로 scope key를 유도해 연다. 이미 검증된 경로다
   (`SyncShadowVerifier`, `SyncShadowReader`).
4. **tombstone 제외** — §6.4.
5. **조립** — `(space_id, room_id, worldline_key)` 단위로 `bubble_order` 정렬해
   원격 저장소에 쓴다(§3.1).
6. **대조** — §6.3의 계약대로 확인한다.

5단계는 **원자적 교체**로 한다. 저장 단위 하나의 파일을 임시 파일에 다 쓰고
rename한다. 부분 적용된 방은 사용자에게 "대화가 잘렸다"로 보이고, 그것은 결함이
아니라 데이터 손실처럼 읽힌다.

### 6.3 대조는 G4에서 사람이 한다 — 자동 대조는 아직 경로가 없다

초안은 "쓴 기기가 보고한 값과 비교한다"고 적었으나 **그럴 데이터 경로가 없다.**
개수와 내용 hash는 writer의 로컬 manifest에만 있고 wire에 실리지 않는다. 실기기
확인 때 대조한 것도 사람이 두 화면의 숫자를 눈으로 비교한 것이었다.

계약을 분명히 한다.

| 단계 | 대조 방식 |
| --- | --- |
| G1~G3 | 시험이 fixture의 expected 값과 비교한다 (자동) |
| **G4** | **사람이 두 기기 화면의 개수·hash를 비교한다 (수동)** |
| 자동 대조 | **미구현.** wire에 manifest를 얹는 별도 계약이 필요하다 |

받는 기기는 자기 hash를 계산해 화면에 **표시**한다. 그러나 기대값이 없으므로
"일치/불일치"를 스스로 판정하지 않는다. **판정하지 않는 것을 판정한 것처럼
표시하지 않는다.**

자동 대조를 열려면 방 단위 manifest(개수·hash)를 암호화해 wire에 실어야 한다.
`extensions.<owner>.room.<field>` 계약이 이미 있으므로 그 위에 얹는 것이 가장
가깝지만, 확정된 설계가 아니다. **§9의 미승인 목록에 둔다.**

### 6.4 tombstone 행은 조립에서 제외한다

`turn`과 `bubble`의 projection에는 `is_tombstoned`가 있다
(`src/sync/projection.ts`). 이를 무시하면 **삭제된 말풍선이 원격 방에서 다시
나타난다.**

규칙.

- `is_tombstoned`가 참인 turn·bubble은 조립에서 제외한다.
- 개수와 내용 hash도 **제외한 뒤** 계산한다. 양쪽이 같은 규칙을 써야 대조가
  의미를 갖는다.
- `is_tombstoned` 필드를 읽지 못하는 행(필드 자체가 없는 경우)은 **적용을
  거부한다.** 없는 것을 거짓으로 간주하면 삭제가 조용히 되살아난다.

**현재는 tombstone 행이 존재할 수 없다.** `delete_turn`이
`RUNTIME_ENABLED_OPERATIONS`에서 빠져 있기 때문이다(결정 15). 따라서 지금까지의
검증 수치는 영향을 받지 않았다. 그래도 규칙과 시험은 지금 넣는다 — 삭제가 열리는
순간 조용히 틀리기 시작하는 종류이기 때문이다.

### 6.5 화면 정렬 — 공간을 가로지르는 순서

`bubble_order`는 공간별이므로 전체 순서를 주지 못한다(§1.1). 화면은 이렇게
정렬한다.

1. 말풍선 평문 metadata의 `timestamp` 오름차순
2. 같으면 `space_id` 사전순
3. 그래도 같으면 `bubble_order` 오름차순

2·3은 순서를 **안정**시키기 위한 것이지 의미가 있는 순서가 아니다. 기기 시계가
어긋나면 순서도 어긋난다. v1은 이를 감수한다.

## 7. 이번 작업에서 배운 것 — 계속 의심할 것

세 결함 모두 **화면상 정상으로 보였다.**

| 결함 | 증상 | 왜 안 보였나 |
| --- | --- | --- |
| 합류 전 account id | 복호화 0/N | 신원·순서·hash는 account와 무관 |
| `_enc` 접미사 | 복호화 0/N | 봉인 필드 없음과 빈 행이 구분 안 됨 |
| `worldline_key` | 없음 (우연히) | 이번 행에 worldline이 없어서 맞았음 |

### 7.1 지금 코드에 남아 있는 결함 — 적용 전에 고쳐야 한다

**두 reader가 `room_id`만으로 행을 거른다. 공간을 보지 않는다.**

- `Sources/KakaoSapiens/Services/SyncShadowReader.swift` — `identity["room_id"]`
  비교만 한다
- `android/.../sync/SyncShadowVerifier.kt` — 동일

지금까지는 `room_id`가 기기별 UUID라 겹치지 않아 드러나지 않았다. **§1.1의
이어가기를 열면 같은 `room_id`가 두 공간에 있는 것이 정상이 되고, 그때 두 공간의
행이 한 방으로 뒤섞여 개수와 hash가 모두 틀린다.** 복호화는 행마다 자기 공간으로
유도하므로 성공하고, 따라서 **화면상으로는 정상으로 보인다** — §7의 다른 결함들과
같은 부류다.

G1에서 두 reader가 `(space_id, room_id)`로 거르도록 고치고, 같은 `room_id`가 두
공간에 있는 fixture로 시험을 고정한다.

### 7.2 계속 의심할 것

적용 단계에서 같은 종류가 나올 자리를 미리 적어 둔다.

- **wire 이름을 손으로 적는 모든 곳.** fixture를 손수 만들면 잘못된 가정이
  양쪽에 똑같이 들어가 사이좋게 통과한다. fixture는 실제 writer가 뽑고, Worker
  시험이 실제 change feed와 대조한다. 이번에 이미 그렇게 바꿨고 유지한다.
- **개수만 맞고 내용이 틀린 경우.** 개수 대조는 통과하는데 순서가 뒤집혔거나
  다른 방 행이 섞였을 수 있다. 내용 hash가 이걸 잡는다. **개수 일치만으로
  성공을 보고하지 않는다.**
- **부분 복호화.** N개 중 일부만 열렸는데 "받았다"고 표시하면 사용자는 잘린
  대화를 정상으로 믿는다. 전부 열리지 않으면 방을 적용하지 않는다.
- **worldline 있는 방.** 방 제목은 null-worldline scope, 말풍선은 worldline
  scope다. 폰 단톡방을 적용할 때 처음으로 실제로 걸린다. 다만 §4에 따라 폰 방은
  어차피 표시하지 않으므로 v1 적용 대상이 아니다.

## 8. 단계별 gate

각 단계는 앞 단계가 통과한 뒤에만 시작한다.

- [ ] **G0 — reader의 공간 필터 수정.** §7.1. 두 reader가 `(space_id, room_id)`로
      거르게 하고, 같은 `room_id`가 두 공간에 있는 fixture로 고정한다.
      **다른 모든 gate의 선행 조건이다.**
- [ ] **G1 — 조립기와 원격 저장소.** 합성 fixture로 선별·복호화·tombstone 제외·
      조립·원자적 교체를 검증한다. 저장 단위는 §3.1. 실기기 없음, 실데이터 없음.
- [ ] **G2 — 소유 공간 불변식.** 자기 공간 행이 적용되지 않는 것을 시험으로
      고정한다. 자기 공간 행을 섞은 replica로 확인한다.
- [ ] **G3 — 노출 규칙.** §4 표의 아홉 칸을 각각 시험으로 고정한다.
      특히 폰 방이 Mac·태블릿에서 걸러지는 것.
- [ ] **G4 — 실기기 적용.** Mac 방 "테스트2"를 폰에 적용한다. 전부 복호화 확인과
      §6.3의 **수동** 개수·hash 대조. **사용자 승인 필요.**
- [ ] **G5 — 화면 표시.** 채팅 목록에 출처 표시와 함께 나타난다. 정렬은 §6.5.
      결정 8번의 답변 방식 안내 1회.
- [ ] **G6 — 이어가기.** §5.1의 미정 항목을 먼저 정한 뒤 답장을 연다.
      **별도 설계와 승인이 필요하다.**
- [ ] **G7 — 범위 확대.** 방 하나가 성공한 뒤에만 다른 방을 연다.

## 9. 이 문서가 승인하지 않는 것

- **이어가기 구현** — 방식은 §1.1에서 정했으나 §5.1의 미정 항목이 남아 있다.
  G6에서 별도 설계와 승인을 거친다. (§1.1 자체를 승인 취소한다는 뜻이 아니다.)
- **delegated writer** — 다른 공간의 행을 직접 고치는 것. 계약이 없고 만들지 않는다.
- **개수·hash 자동 대조** — wire에 manifest를 얹는 계약이 필요하다(§6.3).
- 폰 방을 Mac·태블릿에 표시 (결정 3)
- Mac 방을 태블릿에 표시 (결정 5)
- 원격 방의 수정·삭제 (결정 15)
- 첨부 복사 (아직 경로 없음, 미복사 개수만 보고)
- 자동 동기화 켜기 — 모든 적용은 여전히 버튼 뒤에 둔다
- OS 알림 (결정 14)
