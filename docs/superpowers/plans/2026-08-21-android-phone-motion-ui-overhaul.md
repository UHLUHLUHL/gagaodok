# Android phone UI·모션 대개편 마스터 플랜

상태: 계획 보존 상태. 모든 Phase 미완료.

대상은 Android `phone` 변형이며, 새 모션은 `COMPANION` 모드에만 적용한다. 멘토 모드,
`tabletMentor`, macOS, Obsidian 흐름은 변경하지 않는다.

## 기준과 현재 상태

- 기준 커밋: `3c85387`
- 브랜치: `codex/persona-repetition-control`
- Figma: `https://www.figma.com/design/tYEBz5VicQ9lbd9alrJQgB?node-id=2-2`
- 기존 로컬 HTML 시안과 그 시안을 바탕으로 한 Compose 구현은 폐기했다.
- Figma MCP는 Starter 플랜 호출 한도에 걸렸던 이력이 있으므로, 호출 성공을 실제로 확인하기
  전까지 Figma에 등록됐다고 가정하지 않는다.
- 실제 휴대폰 장기 대화·60Hz 프레임 측정은 아직 하지 않았다.
- 사용자는 최신 실험 APK가 마음에 들지 않아 이전 버전으로 다운그레이드한 상태다.

## 공통 원칙

- 카카오톡 모바일의 밀도·계층·방향성을 유지한다.
- 모션은 기능을 가리거나 기다림을 더 길게 느끼게 하지 않는다.
- 한 상태 전환에서 강조 모션은 하나만 사용하고 나머지는 짧은 opacity로 보조한다.
- 응답 취소·오류·재시도는 성공 경로와 구분하되, 사용자가 언제든 상태를 이해할 수 있어야 한다.
- 기존 저장 데이터·`turnId`·`canonicalText`·API 비용 기록을 보존한다.
- 실제 API 호출과 실기기 설치는 비용·데이터 영향이 있으므로 필요한 최소 흐름만 검증한다.

## Phase 0 — 현재 상태 기준선과 모션 감사

- [ ] 실제 Android phone에서 친구/채팅/설정 진입과 복귀를 녹화한다.
- [ ] COMPANION 응답의 대기, 첫 결과, 다중 말풍선, 완료, 취소, 오류를 녹화한다.
- [ ] `MainActivity.kt`, `RootScreen.kt`, `ChatRoomScreen.kt`, `ChatRoomTyping.kt`의 모션을
  trigger → start → transition → end → interruption으로 표로 정리한다.
- [ ] 각 문제를 연속성·방향성·속도·피드백·성능·접근성으로 분류한다.
- [ ] 60Hz에서 프레임 드롭·입력 지연·스크롤 점프를 기록한다.
- [ ] 이미 좋은 모션과 고칠 모션을 분리한다.

완료 기준: 기준 영상과 수치가 있고, 문제를 재현할 수 있다.

## Phase 1 — Figma Motion 기준과 Compose 공통 토큰

- [ ] Figma 기존 파일에 `Motion Audit`, `Motion Tokens`, `Chat Lifecycle`, `Navigation`,
  `Overlays` 페이지를 만든다.
- [ ] 기존 디자인 시스템·색·타이포그래피·아이콘을 먼저 검색한다.
- [ ] Figma Motion API와 prototype 전환을 실제 호출로 확인한다.
- [ ] `instant`, `quick`, `standard`, `emphasized`, `stagger`의 값과 사용 조건을 정한다.
- [ ] standard/decelerate/accelerate 이징과 필요한 경우에만 사용할 spring을 정한다.
- [ ] 이동 거리 때문에 duration을 무작정 늘리지 않는 규칙을 만든다.
- [ ] Reduced Motion에서 translation·scale·container morph를 제거하는 규칙을 만든다.
- [ ] Compose 전용 토큰 파일과 순수 단위 테스트를 먼저 작성한다.

완료 기준: Figma 토큰과 코드 토큰이 일치하고, 스크린샷·수치로 대조할 수 있다.

## Phase 2 — 채팅 응답 생명주기

### 2A. Figma 시안

- [ ] 현재 동작을 기준 프레임으로 만든다.
- [ ] A안 리듬 정돈, B안 말풍선 모프, C안 앵커드 핸드오프를 각각 만든다.
- [ ] 시작·첫 점·대기 휴지·첫 결과·두 줄 확장·완료의 6개 시점을 비교한다.
- [ ] 짧은 응답·긴 응답·마크다운·수식·이미지 응답을 별도로 확인한다.
- [ ] 취소 영역과 `눌러서 중지` 안내가 안정적인지 확인한다.
- [ ] 사용자의 최종 승인을 기록한다.

### 2B. 구현

- [ ] 승인된 리듬으로 `typingDotLift()`를 교체한다.
- [ ] 대기 항목과 첫 응답이 안정적인 presentation key를 공유하게 한다.
- [ ] 아바타·이름·말풍선 시작점을 유지한다.
- [ ] 스트리밍 중 목록 전체 스크롤 점프를 방지한다.
- [ ] 완료 시 커서와 진행 표시를 조용히 정착시킨다.
- [ ] 취소·네트워크 오류·재시도를 구별한다.
- [ ] 화면 이탈·백그라운드 진입 시 반복 애니메이션을 중단한다.

완료 기준: Figma 시안과 실기기 영상이 일치하고, 긴 대화에서 스크롤 위치가 보존된다.

## Phase 3 — 내 메시지 전송과 말풍선 변화

- [ ] 전송 버튼의 enabled/pressed/sending 상태를 Figma에서 설계한다.
- [ ] 텍스트 제거·키보드·새 말풍선 삽입 순서를 고정한다.
- [ ] 새 말풍선은 화면 밖에서 날아오지 않는 짧은 fade/translation으로 보인다.
- [ ] 연속 전송의 stagger 상한을 정한다.
- [ ] 실패·재전송과 성공 상태를 시각적으로 구분한다.
- [ ] 수정 완료·삭제 후 주변 말풍선 재배치를 연결한다.
- [ ] 날짜 구분선과 말풍선 꼬리 재계산을 검증한다.

완료 기준: 빠른 연속 입력·전송 실패·재전송에서 메시지 순서와 시각 상태가 정확하다.

## Phase 4 — 입력창·키보드·검색·편집

- [ ] 키보드 열림·닫힘과 목록 스크롤 보정 순서를 검증한다.
- [ ] 첨부 메뉴가 입력창에서 이어지는 형태로 열리고 닫히게 한다.
- [ ] 검색 바 등장 시 헤더 요소가 겹치거나 순간 삭제되지 않게 한다.
- [ ] 검색 결과 이동과 현재 결과 강조를 연결한다.
- [ ] 편집 바의 진입·확정·취소 전환을 통일한다.
- [ ] IME animation 지원 기기와 미지원 기기의 fallback을 확인한다.

완료 기준: 키보드·검색·편집을 빠르게 반복해도 본문·포커스·스크롤이 튀지 않는다.

## Phase 5 — 화면 이동·루트 탭·오버레이

- [ ] `MainActivity.kt`의 좌우·상하 전환을 공통 토큰으로 치환한다.
- [ ] 앞으로 이동·뒤로가기·모달 진입의 방향 규칙을 고정한다.
- [ ] 루트 탭은 페이지 이동보다 fade 중심으로 유지한다.
- [ ] 프로필·말투 편집·설정 상세 화면의 계층 전환을 통일한다.
- [ ] scrim → surface → contents 순서로 다이얼로그·바텀시트를 검증한다.
- [ ] predictive back과 충돌하지 않는지 확인한다.

완료 기준: 화면 계층을 거꾸로 인식하게 만드는 전환이 없다.

## Phase 6 — 목록과 미세 상호작용

- [ ] 채팅방 생성·삭제·고정·순서 변경 시 행이 자연스럽게 양보한다.
- [ ] 친구·채팅·설정 행 pressed 상태와 전환 시작을 맞춘다.
- [ ] 스위치·선택 행·확인 버튼 토큰을 통일한다.
- [ ] 삭제·초기화는 일반 선택과 다른 피드백을 사용한다.
- [ ] 햅틱은 전송·선택 확정·위험 작업 확인에만 제한한다.

완료 기준: 빠른 조작에서 행 겹침·오선택이 없고 햅틱과 시각 피드백이 같은 사건을 가리킨다.

## Phase 7 — 아이콘 광학 보정과 상태 모션

- [ ] 아이콘을 용도·크기·선 굵기·fill/stroke·터치 영역으로 목록화한다.
- [ ] Figma 24dp 상자에서 잉크 중심과 광학 중심을 비교한다.
- [ ] 탭·보내기·뒤로가기·검색·첨부·설정을 우선 검토한다.
- [ ] path morph 대신 색·alpha·scale 중 최소 조합을 사용한다.
- [ ] 시각 크기와 별개로 터치 영역 48dp를 유지한다.
- [ ] 라이트·다크·disabled·pressed·selected를 한 세트로 검증한다.

완료 기준: 아이콘이 기능적으로 맞고 광학적으로 중심에 있으며 모든 상태가 일관된다.

## Phase 8 — 통합·성능·접근성·실기기

- [ ] phone debug 단위 테스트와 UI 테스트를 통과한다.
- [ ] JDK 17로 phone release APK를 빌드한다.
- [ ] 시스템 애니메이션 배율 1×·0.5×·0×를 확인한다.
- [ ] TalkBack에서 로딩·완료·오류가 중복 낭독되지 않는지 확인한다.
- [ ] 큰 글꼴·다크 모드·세로 화면·작은 화면 clipping을 확인한다.
- [ ] 긴 대화·빠른 전송·취소·네트워크 오류를 반복한다.
- [ ] 필요한 경우에만 Compose recomposition·Perfetto·Macrobenchmark를 추가한다.
- [ ] Phase 0 기준 영상과 최종 영상을 나란히 비교한다.

완료 기준: 기능 회귀·접근성 회귀·성능 회귀가 없다는 실제 증거가 있다.

## 실행 규칙과 커밋 경계

1. 한 번에 한 Phase만 진행한다.
2. Figma 시안·스크린샷·구현 계획을 먼저 남긴다.
3. 구현은 TDD로 작은 단위부터 한다.
4. Phase별 phone 테스트를 통과시킨 뒤 release 빌드는 마지막에 한 번 수행한다.
5. 실기기 검증 전에는 Phase를 완료 표시하지 않는다.
6. 사용자 승인 없이 `main`에 병합하지 않는다.
7. API 호출·실기기 설치·사용자 데이터 접근은 필요한 범위를 먼저 확인한다.

## 중단 지점에서 다시 시작하는 방법

Figma MCP가 다시 가능해지면 기존 파일 node `2:2`의 metadata와 screenshot을 먼저 읽는다.
그 다음 Phase 0 기준선과 Phase 1 토큰부터 Figma에 등록한다. 과거 로컬 HTML을 최종 디자인으로
간주하지 말고, A/B/C를 새로 비교해 사용자 승인을 받은 후 구현한다.
