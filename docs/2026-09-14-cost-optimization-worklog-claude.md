## 2. 고친 결함들 — 원인과 근거

### 2.1 `thinkingLevel: high`가 출력 예산을 통째로 먹었다 (`c5de63f`)

**증상**: 기억 갱신이 `finishReason: MAX_TOKENS`로 잘려 성공률 8.33%.

**원인**: Gemini 3.x의 `maxOutputTokens`는 **사고 토큰을 포함**합니다. 그리고
`high`는 주어진 예산이 얼마든 **약 96%를 사고에 씁니다.**

| 준 예산 | 사고가 먹은 비율 |
|---|---|
| 3,500 | 96.06% |
| 10,692 | 95.98% |

→ **예산을 올려서는 못 고칩니다.** 올린 만큼 사고가 따라 늘어납니다.

**고친 내용**: 기억·요약 계열 호출을 `MEMORY_THINKING_LEVEL = "low"`로.
적용 지점 네 곳 — `AIServicePhoneMemory`, `AIServiceDigest`, `AIServicePersona`(2곳).
고친 뒤 실측 사고 토큰 **0**.

> **처음에 제가 틀렸던 것**: 사용자가 "요약은 자주 하는 작업이 아니니 품질을 위해
> `high`가 맞다"고 반박했고 비용 논리는 사용자가 옳았습니다(요약은 50턴당 1회).
> 제가 `low`를 권한 근거가 비용이었던 게 틀렸습니다. 진짜 이유는 **잘림**이었고,
> 그건 둘 다 몰랐습니다. 결론은 같지만 이유가 달랐습니다.

**Codex 확인 사항**: 같은 패턴이 `AIServicePersona.kt:530,532 / :577,579`에도
있었습니다. 말투 추출·교정도 같은 함정입니다.

### 2.2 출력 예산이 몸통 크기와 무관하게 고정이었다 (`d6149f8`)

`AIServiceTransport.kt`에 공통 헬퍼를 뒀습니다.

```kotlin
internal const val GEMINI_MAX_OUTPUT_TOKENS = 8192        // 채팅 답변용, 모델 한도 아님
internal const val GEMINI_MODEL_MAX_OUTPUT_TOKENS = 65_536
internal const val THINKING_HEADROOM = 8192
internal fun outputBudget(bodyTokens: Int): Int =
    minOf(bodyTokens + THINKING_HEADROOM, GEMINI_MODEL_MAX_OUTPUT_TOKENS)
internal const val MEMORY_THINKING_LEVEL = "low"
```

기억 갱신은 `phoneMemoryOutputBudget(segmentCount)` =
`outputBudget(segmentCount × SEGMENT_TOKEN_BUDGET + 1000)`.

> **`THINKING_HEADROOM`을 줄이면 더 아낄까?** 아닙니다. `maxOutputTokens`는
> **상한이지 예약이 아닙니다.** 안 쓰면 안 냅니다. `low`에서 실측 사고가 0이므로
> 줄여 봐야 아끼는 것은 0이고 잘릴 위험만 생깁니다. 제가 한 번 제안했다가 철회한
> 내용입니다.

### 2.3 M3 상태가 가득 차면 요약 전체가 버려졌다 (`8a848b5`, `19f37f9`)

**이게 가장 비쌌던 결함입니다.**

3계층 기억에서 M3(상태)는 **고정 키 8개**(`addressing`, `place`, `time`,
`relationship`, `tone`, `participants`, `inProgress`, `lastEmotionalShift`)와
**무한히 늘어나는 규칙**(`boundary:*`, `loop:*`)이 **한 예산**을 나눠 씁니다.

옛 동작: 넘치면 `require(...)`가 터져 **갱신 전체를 거부**. 그러면 같이 온
**50턴짜리 M2 요약까지 함께 버려집니다.** 그래서 한 번 차면 영구히 멈춥니다.

고친 내용 두 가지.

1. **예산 800 → 3,000토큰** (`STATE_TOKEN_BUDGET`)
2. **저하(degradation) 설계** — 거부 대신 가장 덜 영구적인 것을 놓아줍니다.
   - `loop:*`는 최대 10개(`LOOP_RULE_LIMIT`)
   - 넘치면 `setAtTurn`이 가장 오래된 `loop`부터 버림
   - **`boundary:*`는 절대 안 버림** (사용자가 그은 선은 잊으면 안 됨)
   - 버릴 `loop`가 하나도 없을 때만 거부
   - 버린 개수는 `droppedLoopRules`로 계기에 남김

실패 사유도 갈라 적습니다: `PARSE_FAILED`, `RANGE_MISMATCH`, `SEGMENT_TOO_LONG`,
`STATE_REJECTED`, `NOT_STOP`(+`failureDetail`). 전부 `paid = true`입니다.

> **`require` 메시지에 숫자를 넣지 마세요.** 계기에서 집계 키로 쓰므로 숫자가
> 들어가면 같은 원인이 전부 다른 항목으로 흩어집니다.

### 2.4 캐시 재생성 사유가 뭉뚱그려져 있었다 (`5fe52b2`)

`CacheCreateReason.FIRST`가 **다섯 가지 원인을 뭉치고** 있었습니다. 만료된 캐시는
로컬 기록에서 지워지므로 다음 생성 때 "이 방엔 캐시가 없다"로 보였고, TTL을 늘려
줄이려던 바로 그 사건이 `FIRST`에 섞였습니다.

`CacheDropReason`(`MODEL_CHANGED`, `EXPIRED`, `SHRUNK`, `FINGERPRINT_CHANGED`)을
버릴 때 기록하고, 생성 때 `CacheCreateReason.from(drop)`으로 이어 받습니다.

**이 계기가 없었으면 09-14의 발견은 불가능했습니다.** 아래 3장이 전부 이 숫자에서
나왔습니다.

> **제 코드 주석이 틀렸던 것**: "TTL 효과는 `EXPIRING_SOON`의 감소로 나타난다"고
> 적었는데, 만료로 인한 재생성은 `EXPIRED`로 갑니다. **TTL 효과는 `EXPIRED` +
> `EXPIRING_SOON`의 합으로 읽어야 합니다.**

### 3.2 왜 줄어드는가 — 사용자 행동

| 근거 | 비율 |

사용자 확인:
> "마음에 안 드는 답변이 나오면 수정 눌러서 다시 보낸다. 딱히 입력하는 채팅을

`truncateFrom`이 **그 뒤를 전부 잘라낸 뒤 다시 생성**합니다. 옛 답장은 지워지므로
메시지 수는 그대로인데 요청만 늘어납니다.

그리고 잘라내면 `contents.size`가 줄어 `AIServicePrefixCache.kt:153`이 캐시를
통째로 버립니다 — **`SHRUNK`의 정체입니다.**

> **분포 교차 검증**: 재요청 203회 중 `SHRUNK` 36회 = 17.7%.
> "마지막 턴만 다시 받는데 그게 캐시 생성 직후에 걸린 경우"의 이론값은

### 3.3 고친 내용

캐시가 덮는 범위를 대화 끝에서 **한 교환**(`CACHE_LAG_ENTRIES = 2`) 뒤로 물립니다.

```kotlin
internal fun prefixCacheLagEntries(
    entryCount: Int, laggedPrefixTokens: Int, shrinkProne: Boolean
): Int {
    if (!shrinkProne) return 0                              // 고쳐 쓴 적 없는 방
    if (entryCount <= CACHE_LAG_ENTRIES) return 0           // 접두사가 안 남음
    if (laggedPrefixTokens < MINIMUM_CACHE_TOKENS) return 0 // 최소치 아래로 떨어짐
    return CACHE_LAG_ENTRIES
}
```

**같이 안 고치면 버그가 나는 세 곳** — 범위만 줄이면 마지막 교환이 캐시와 요청에
**두 번** 실립니다.

```kotlin
val prefix = if (lag > 0) contents.dropLast(lag) else contents
// 1) 올리는 내용
.put("contents", JSONArray().apply { prefix.forEach { put(it) } })
// 2)(3) 범위와 지문
coveredTurns = prefix.size,
fingerprint  = fingerprint(prefix, system),
lagEntries   = lag
```

**갱신 주기가 짧아지지 않게 하는 보정**도 필요합니다. 물린 꼬리는 처음부터 캐시
밖이었으므로 "새로 붙은 것"이 아닙니다.

```kotlin
// CACHE_CURRENT 판정
if (previous.coveredTurns + previous.lagEntries >= contents.size && ...) 
// 꼬리 크기 (= 만든 뒤 새로 붙은 양)
val tail = estimateTokens(contents.drop(previous.coveredTurns + previous.lagEntries))
```

이 보정이 없으면 꼬리가 상시 한 교환만큼 커 보여 재생성이 잦아지고, **물린 대가를
재생성 횟수로 또 냅니다.**

> **제가 중간에 틀렸던 것**: "`SHRUNK`을 없애도 재생성이 `TAIL_GREW`로 옮겨가

## 6. 재요청 때 비슷한 답이 오는 문제 — **씨앗은 무관. 기각**

### 6.1 시험

`docs/seed-probe.sh` · 모델 `gemini-3.8-flash` · 호출 12회
질문: **"처음 보는 행성을 하나 상상해서 이름과 특징을 딱 한 문장으로 말해줘.
매번 다른 것을 지어내."** (경우의 수가 많아야 무작위성을 잴 수 있습니다)

| 구간 | 조건 | 서로 다른 답 |
|---|---|---|
| **A** | seed 없이 5회 | **5 / 5** |
| **B** | seed 11·22·33·44·55 | 5 / 5 |
| **C** | **같은 seed 77로 2회** | **2개가 서로 다름** |

**A**: 씨앗을 안 줘도 이미 매번 다른 답이 옵니다. 공식 레퍼런스의 "`seed`를
생략하면 요청마다 무작위 씨앗을 만든다"와 일치합니다.

**C가 결정적입니다.** 같은 씨앗을 줘도 답이 고정되지 않습니다.

```
C1(seed=77): ... 보랏빛 사막 행성 '루미나리스-9'입니다.
C2(seed=77): 대기가 핑크빛 프리즘처럼 빛나는 행성 '루미아라'는 ...
```

씨앗이 출력을 정하지 못하므로, **무작위 씨앗을 넣는 것은 아무 일도 하지 않습니다.**

### 6.2 결론 — 기각

`2082eb2`를 `6ddec38`로 되돌렸습니다. 비용이 0이어도 지웁니다. `nextRequestSeed()`
와 "재요청 때 답이 갈리게 한다"는 주석, 그것을 검사하는 테스트 5개가 남아 있는데
**실제로는 아무 일도 하지 않습니다.** 읽는 사람을 속이므로 없는 것보다 나쁩니다.

`docs/seed-probe.sh`는 남깁니다 — 이 결론의 근거이고, 모델이 바뀌면 다시 잽니다.

### 6.3 우리가 틀렸던 방식

1판 시험은 **"좋아하는 과일 다섯 개를 나열해줘"**를 두 번 물어 같은 답이 나온 것을
"씨앗 없이는 결정적"의 증거로 삼았습니다.

- **답이 뻔한 질문은 씨앗이 무엇이든 같은 답이 나옵니다.** 경우의 수가 없는 질문으로
  무작위성을 재려 했습니다.
- **대조군이 없었습니다.** 씨앗 없이 반복해 보지 않았으므로, 기기에서 재요청 3회가
  갈린 것이 우리 수정 때문인지 원래 그런지 구분할 수 없었습니다.

Codex 검토에서 걸렸습니다. 교훈 둘입니다.

1. 무작위성을 잴 때 답이 뻔한 질문을 쓰지 말 것.
2. **대조군 없이 인과를 주장하지 말 것.**

### 6.4 진짜 원인은 따로 있습니다

사용자가 겪은 "다시 받아도 비슷한 답"은 **결정성 문제가 아니었습니다.**
위 12개 답의 행성 이름을 뽑으면 이렇습니다.

> 루미나-9 · 루미아니스 · 루미아니스 · 크리올리스 · 루미나크라 · 크리올리스
> 루미나-IX · 루미아니스 · 크리스탈리아 · 크리올리스 · 루미나리스-9 · 루미아라

**12개 전부가 `루미-` 아니면 `크리-`로 시작합니다.** 루미아니스가 3번, 크리올리스가
3번 그대로 반복됩니다. 내용도 전부 "결정·프리즘이 빛을 굴절시켜 무지개·오로라가
생기는 행성"입니다. 프롬프트에 **"매번 다른 것을 지어내"**라고 명시했는데도요.

| | 처음 진단 | 실제 |
|---|---|---|
| 증상 | 답이 **똑같이** 온다 | 글자는 다르고 **알맹이가 비슷**하다 |
| 원인 | 씨앗이 고정 | **모델이 한 갈래로 쏠린다** |
| 처방 | 씨앗 바꾸기 | **씨앗으로는 안 풀림** |

긴 역할극이면 문맥과 페르소나가 답을 더 좁히므로 쏠림이 더 심할 것입니다.
**입력을 바꾸는 것**(사용자가 이미 하는 "조금 고쳐서 다시 보내기")이 실제로 듣는
방법이고, 이 데이터가 그것을 뒷받침합니다. 프롬프트에 문구를 넣는 방식은 사용자가
원치 않으므로 제안하지 않습니다.

## 8. Codex가 같은 함정에 안 빠지려면

같은 앱을 건드린다면 아래는 실측으로 확인된 것들입니다.

1. **`maxOutputTokens`에 사고가 포함됩니다.** `high`는 예산의 96%를 먹습니다.
   예산을 올려서는 절대 못 고칩니다. 요약·추출 계열은 `low`로.
2. **`maxOutputTokens`는 상한이지 예약이 아닙니다.** 넉넉히 잡는 것 자체는 공짜지만,
   잘려 있던 사고가 길어질 여지를 주는 것은 공짜가 아닙니다.
3. **넘칠 때 전체를 거부하지 마세요.** M3가 넘쳐서 50턴짜리 M2 요약까지 함께
   버려졌고, 그래서 **영구히 멈췄습니다.** 덜 중요한 것부터 놓아주세요.
4. **계기의 사유를 뭉뚱그리지 마세요.** `FIRST` 하나가 다섯 원인을 덮고 있어서
   TTL 변경의 효과를 1년 가까이 못 읽었습니다.
5. **캐시 범위를 대화 전체로 잡지 마세요.** 사용자가 고쳐 쓰는 순간 깨집니다.
   물릴 거면 **올리는 내용·지문·범위 셋을 함께** 줄이고, 꼬리 계산도 보정하세요.
6. **토큰 추정기가 사진을 세게 하세요.** 안 그러면 제일 비싼 방이 캐시를 못 받습니다.
7. **`require` 메시지에 숫자를 넣지 마세요.** 집계 키로 씁니다.
8. **Gemini 3.x는 `temperature`/`topK`/`topP`를 무시합니다.** 남은 손잡이는
   `seed`뿐이고, 변경 안내문에 없다고 해서 미지원이 아닙니다(안 바뀐 것입니다).
   `generationConfig`는 캐시에 안 담기므로 씨앗을 바꿔도 캐시는 안 깨집니다.
9. **무작위성을 잴 때 답이 뻔한 질문을 쓰지 마세요.** 우리가 그렇게 하고
   "결정적이다"라고 결론 냈습니다. **대조군 없이 인과를 주장하지 마세요.**
9. **빌드 성공은 동작 확인이 아닙니다.** 위 4장은 실제 기기에서 계기 숫자가
   움직이는 것을 보고 쓴 것입니다.
