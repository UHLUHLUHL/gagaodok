## 1. 1차 결함 — `thinkingLevel: high` + 좁은 `maxOutputTokens`

### 1.1 실측

같은 방(room-12)의 기억 갱신 호출이다.

| | run-7 | run-8 (예산만 3배) | run-8 (`low`) |
|---|---|---|---|
| `maxOutputTokens` | 3,500 | 10,692 | 10,692 |
| 사고 최대 | 3,362 | **10,262** | **0** |
| 예산 대비 | **96.06%** | **95.98%** | 0% |
| 본문 | 258 | 866 | **1,068** |

**예산을 3배로 올렸더니 사고도 정확히 3배가 됐다. 두 번 다 96%다.**
`high`는 줄 수 있는 것보다 훨씬 더 생각하려 하고 예산 끝에서 잘린다.
**예산을 올리는 방향으로는 이길 수 없다.**

`low`로 내리자 사고가 **0**이 되고 본문이 지시한 목표(구간당 900~1,100)에 정확히
들어왔다.

### 1.2 판정을 가능하게 한 것

```
09-10 21:26 I PhoneMemory: outcome=NOT_STOP why=MAX_TOKENS coverage=300→300 target=350
```

`why=MAX_TOKENS`는 커밋 `d6149f8`에서 새로 남기기 시작한 필드다. 그 전에는
`finishReason != "STOP"`을 전부 `NOT_STOP` 하나로 합치고 있었다. 출력 한도와 안전
필터는 처방이 정반대인데 장부에서는 같아 보였다. **이 한 필드가 없었으면 예산을
또 올려보고 또 실패했을 것이다.**

### 1.3 공식 문서

- `max_output_tokens`는 **사고 토큰을 포함한다** — "including thought tokens".
- 잘림을 피하려면 예산이 아니라 **`thinking_level`을 낮추라**고 안내한다.
- Gemini 3에서는 사고량을 **숫자로 지정할 수 없다.** `low`/`medium`/`high` 셋뿐이다.
  `thinkingBudget`은 하위 호환으로 받되 예상 못 한 동작을 낼 수 있다고 경고한다.
  따라서 **"`high`로 두되 3,000토큰만 생각해라"는 불가능하다.**
- Gemini 3.7 Flash 출력 한도는 **65,536**이다.

출처: [thinking](https://ai.google.dev/gemini-api/docs/generate-content/thinking) ·
[gemini-3.7-flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.7-flash)

경로는 `android/app/src/main/java/com/sapiens/gagaodok/service/`.

| `AIServicePhoneMemory.kt:119` | 8,192 (코덱스가 이미 수정) | 폰 3층 기억 갱신 | **실측 확인됨** |
| `AIServiceDigest.kt:86`, `:89` | 2,700 | 멘토·비 companion 구간 요약 | **계측 사각지대** |
| `AIServicePersona.kt:530`, `:532` | 2,048 | **말투 분석** | 사용자에게 잘못된 안내 |

**멘토 경로는 계측이 없다.** `AIServiceConversation.kt`의 `measure` 플래그가
`!TABLET_MENTOR && COMPANION`이라 실패해도 어디에도 안 잡힌다. 게다가

**즉시 재시도한다.** 백오프가 없다.

**말투 쪽은 조용히 실패하지는 않는다.** `emptyResponseMessage`가 사용자에게

**그 안내가 틀렸다.** 대사를 나눠 넣어도 사고가 예산을 먹는 것은 그대로다.

### 1.5 코덱스 브랜치의 현재 값 — **이 방향으로는 안 된다**

```kotlin
// PhoneMemoryPolicy.kt:18-24
internal const val PHONE_MEMORY_POLICY_FINGERPRINT = "phone-memory-v2-high-8192-r1500-backoff-v1"
internal const val PHONE_MEMORY_THINKING_LEVEL = "high"
internal fun phoneMemoryOutputBudget(rangeCount: Int): Int =
    (8_192L + 1_500L * (rangeCount - 1)).coerceAtMost(...).toInt()
```

예산을 3,500 → 8,192로 올리고 `high`를 유지했다. **우리가 실측으로 기각한 조합이다.**
우리도 같은 판단을 했다가 실기기 데이터에 뒤집혔다.

96% 비율을 적용하면 사고가 약 7,864를 먹고 본문에 **328토큰**이 남는다. 필요한 것은
약 2,500이다. 두 관측점(3,500·10,692) 사이의 내삽이므로 예측이지 관측은 아니다.

정책 지문 `phone-memory-v2-**high-8192**-r1500-backoff-v1`도 함께 바꿔야 한다.
값이 바뀌면 지문도 바뀌어야 재시도 상태가 옛 정책의 것과 섞이지 않는다.

### 1.6 우리가 한 수정

`AIServiceTransport.kt`에 공용 헬퍼를 뒀다. `GEMINI_MAX_OUTPUT_TOKENS = 8192`가 이미
있는데 그것은 **채팅 답변 길이를 정하려고 고른 값이지 모델 한도가 아니다.** 뜻이
다르므로 따로 둔다 — 같은 이름으로 묶으면 한쪽을 바꿀 때 다른 쪽이 조용히 따라간다.

```kotlin
internal const val GEMINI_MODEL_MAX_OUTPUT_TOKENS = 65_536
internal const val THINKING_HEADROOM = 8192
internal fun outputBudget(bodyTokens: Int): Int =
    minOf(bodyTokens + THINKING_HEADROOM, GEMINI_MODEL_MAX_OUTPUT_TOKENS)
internal const val MEMORY_THINKING_LEVEL = "low"
```

네 곳 모두 `outputBudget(본문) + MEMORY_THINKING_LEVEL`로 바꿨다.

| 호출 | 본문 | 예산 |
|---|---|---|
| 폰 기억 (1구간) | 2,500 | 10,692 |
| 멘토 구간 요약 | 2,700 | 10,892 |
| 말투 분석 | 2,048 | 10,240 |
| 말투 교정 | 2,560 | 10,752 |

사고 몫을 본문 분량과 무관하게 같은 크기로 붙이는 것은, 사고량이 답이 길어서 느는
것이 아니라 그 작업이 어려워서 늘기 때문이다.

**`THINKING_HEADROOM = 8192`에는 근거가 없다.** `low`의 실제 사고량이 측정될 때까지의
임시값이다. 실측에서 `low`는 0을 썼으므로 다음 회차에서 줄일 수 있다.

## 2. 2차 결함 — M3 상태 포화 (코덱스 브랜치에 그대로 있음)

1차를 고치자 다음 벽이 드러났다. 그 호출은 사고 0, 본문 809토큰으로 **정상 종료했는데**
`STATE_REJECTED`로 끝났다.

### 2.1 무엇이 문제인가

M3 상태가 상한에 닿아 있었다. 렌더 928자 = **761토큰, 상한 800. 여유 48자.**
50턴 분량의 새 사건을 반영하려면 그보다 훨씬 많이 필요하다.

**M3가 성격이 다른 둘을 한 통에 담고 있다.**

| | 개수 | 토큰 | 성격 |
|---|---|---|---|
| 고정 키 8개 | 8 | ~440 | **상태.** 매번 덮어쓰고 안 자람 |
| `boundary:*` / `loop:*` | 10 | ~750 | **규칙.** 한 번 생기면 안 없어짐 |

체크포인트 여섯 개(200·250·300·350·400·450턴)를 뽑아 확인했다.

```
200턴  10항목 494토큰 (고정 380, bnd 1, loop 1)
250턴  10항목 523토큰 (고정 409, bnd 1, loop 1)
300턴  13항목 761토큰 (고정 430, bnd 2, loop 3)
350턴  15항목 895토큰 (고정 429, bnd 3, loop 4)
400턴  16항목 995토큰 (고정 440, bnd 4, loop 4)
450턴  18항목1189토큰 (고정 440, bnd 4, loop 6)

선형 적합 M3 ≈ 2.87×턴 − 124   R²=0.976
250턴 동안: 규칙 +8개, 삭제 0개
```

**고정 키는 380→440으로 안정적이다. 규칙만 자란다. 그리고 하나도 안 사라진다.**

### 2.2 넘치면 무슨 일이 나나 — 이것이 진짜 결함이다

```kotlin
// 코덱스 브랜치 ThreeLayerMemory.kt:76 (우리 브랜치도 같았다)
require(items.size <= 40 && TokenEstimator.textTokens(renderItems(items)) <= 800)
```

`reduce`가 예외를 던지면 상태만 거부되는 것이 아니다. **그 시도의 M2 구간 요약까지
함께 버려진다.** 809토큰짜리 요약이 상태 40토큰 때문에 폐기됐다.

입력이 같으니 다음 시도도 같은 결과다. **요약 범위가 영구히 멈춘다.** 실제로 300턴에서
멈춰 있었다.

그리고 지시문이 못을 박고 있다 — **"경계·약속을 분량 때문에 삭제하지 마라."**
상한을 지킬 유일한 방법을 금지한 채 상한을 요구한다.

### 2.3 설계 — 다섯 안을 정량 비교했다

486턴 → 1,500턴 시뮬레이션. 위 실측 증가율(boundary 83턴/개·65토큰,
loop 50턴/개·80토큰)로 돌렸다.

| 안 | 합계$ | 막힘 | 끝 입력 | **경계 버림** | loop 버림 |
|---|---|---|---|---|---|
| 800~1200 / 저하✗ (현재) | 49.61 | **529턴** | 460,268 | 0 | 0 |
| 3000 / 저하✗ | 12.22 | **1279턴** | 146,965 | 0 | 0 |
| 1200 / 저하✓ | 5.92 | — | 40,168 | **5.6** ⚠️ | 25 |
| 3000 / 저하✓ | 6.04 | — | 41,968 | 0 | 7 |
| **3000 / 저하✓ + loop 10** | **5.99** | — | 41,251 | **0** | 16 |

**셋이 드러났다.**

1. **저하만 있으면 비용은 어느 안이든 같다** ($5.92~6.04, 차이 2%). 상한 크기는
   비용 문제가 아니다. 갈리는 것은 **무엇을 잊느냐**뿐이다.
2. **상한이 낮으면 경계까지 버린다.** 1200/저하는 경계를 5.6개 버렸다. 중요한
   규칙일수록 일찍 정해지므로 오래된 순으로 버리면 **가장 중요한 것부터** 사라진다.
3. **상한만으로는 안정되지 않는다.** 3000/저하는 1500턴에 이미 상한에 붙어 그 뒤로
   계속 버려야 한다. loop 개수를 묶으면 상태가 약 2,283토큰에서 **수렴**한다.

### 2.4 우리가 한 수정 (`19f37f9`)

```kotlin
const val STATE_TOKEN_BUDGET = 3000        // 안전망
internal const val LOOP_RULE_LIMIT = 10    // 실질 방어선

data class MemoryItem(..., val setAtTurn: Int = 0)   // 마지막 갱신 시점
data class MemoryReduction(val items: List<MemoryItem>, val droppedLoops: Int = 0)

fun reduce(previous, updates, evidence, throughTurn: Int = 0): MemoryReduction
```

- **`loop` 최대 10개.** 가장 오래 갱신 안 된 것부터 놓는다. 상태의 41%를 차지하면서
  가장 빨리 자라고 가장 덜 영구적이다.
- **`boundary`는 놓지 않는다.** 지켜야 하는 약속이다.
- **상한 3,000은 안전망.** 평소에는 개수 제한이 먼저 걸린다.
- **놓을 `loop`이 없는데도 넘치면 그때는 거부한다.** 경계만으로 상한을 넘는 상황은
  사람이 봐야 한다. 조용히 경계를 버리는 것이 가장 나쁜 결말이다.

`setAtTurn`은 규칙이 다시 언급되면 다시 `set`되므로 **"최근 활동"에 가까운 신호**가
된다. 옛 기록에는 없어 0이고, 그것들이 실제로 가장 오래된 것이라 먼저 놓는 것이 맞다.

**놓아준 수를 `MeasurementMemory.droppedLoopRules`에 쌓는다.**
조용히 잊는 것이 가장 나쁜 결말이라 **이 계측 없이는 이 설계를 쓰면 안 된다.**

### 2.5 기존 테스트를 일부러 뒤집었다

`ThreeLayerMemoryTest.oversizedStateIsRejectedWithoutEviction`이 **"넘쳐도 밀어내지
않는다"를 보장하고 있었다.** 그 보장이 요약을 영구히 멈추게 했다.

지우지 않고 `oversizedStateEvictsLoopsButKeepsBoundaries`로 다시 썼다. 원래 지키려던
것 — 경계를 함부로 밀어내지 않는다 — 는 그대로 지킨다.

**코덱스 브랜치에도 같은 테스트가 있을 것이다.** 같은 판단을 하려면 이 문단을 근거로
쓰면 된다.

| 200~450턴 평균 | 2.78토큰/턴 |
| **450~550턴** | **1.13토큰/턴 (−59%)** |

- **`boundary`: 4개 → 4개. 100턴 동안 증가 0.**
- `loop`: 6 → 7. 50턴당 1개였던 것이 100턴당 1개로.

2판에서 "경계가 선형이면 2,367턴에서 상한에 닿는다"고 했는데 **포화 쪽 증거가 나왔다.**
최근 추세로는 3,000 도달이 2,052턴이다. **표본이 1구간뿐이라 확정은 아니다.**

`setAtTurn`은 의도대로 붙었다 — 새로 생긴 규칙만 550, 나머지는 0. 다시 언급되지
않은 규칙이 0으로 남아 먼저 버려질 후보가 된다. 실제로 가장 오래된 것들이라 맞다.

**저하는 아직 한 번도 발동하지 않았다** (`droppedLoopRules 0`, loop 7/10).

### 3.4 새 계측이 찾아낸 것 — 캐시를 깨는 주범은 TTL이 아니다

```
createReasons: {SHRUNK: 19, EXPIRED: 8, FIRST: 5, EXPIRING_SOON: 3, TAIL_GREW: 3}
```

| 원인 | 건수 | 비중 |
|---|---|---|
| **`SHRUNK`** (대화가 짧아짐) | **19** | **50%** |
| `EXPIRED` + `EXPIRING_SOON` (TTL) | 11 | 29% |
| `FIRST` | 5 | 13% |
| `TAIL_GREW` | 3 | 8% |

**이 전부가 예전에는 `FIRST` 하나에 뭉쳐 있었다.**

원인은 `AIServicePrefixCache.kt`의 `coveredTurns = contents.size`다. **캐시가 접두사
전체(마지막 턴까지)를 덮는다.** 그래서 답변 하나를 지우거나 다시 만들면
`contents.size <= cache.coveredTurns`가 참이 되어 캐시가 통째로 버려진다.
요약이 진행될 때도 원문이 80→30턴으로 줄어 한 번씩 발생하는데, 그건 2건뿐이다.

**고치는 방법은 마지막 K턴을 캐시에서 빼는 것이다.** 그러면 최근 K턴이 바뀌어도
캐시가 살아남는다. 대가는 K턴이 항상 캐시 밖에 있는 것이다.

> **4판: 이것을 실제로 했다(`8542b53`, 8장).** 3판에서 "손익이 뒤집힐 수 있어
> 손대면 안 된다"고 적었는데, 다시 계산해 보니 **과금 여부와 무관하게 이득**이다.
> 이득의 절반 이상이 "캐시 없이 전액으로 나가던 요청"을 되찾는 것인데, 그 항목은
> 생성 과금과 아무 상관이 없다. K는 4가 아니라 **2엔트리(한 교환)**로 정했다.

## 8. 캐시 물림 — 3.4절을 실제로 고쳤다 (`8542b53`)

### 8.1 왜 줄어드는가 — 사용자 행동이 원인이다

장부와 대화 파일을 맞대 보니 **사용자 메시지 174개에 API 요청이 377건**이었다
(2.17배). 결제 대시보드의 24시간 집계도 1.93배로 같은 그림이다.

사용자 확인: "마음에 안 드는 답변이 나오면 수정 눌러서 다시 보낸다. 딱히 입력하는
채팅을 바꾸지 않고 보내는 일도 많다."

`MessageResendLogic.truncateFrom`이 그 뒤를 전부 잘라내고 다시 생성한다. 옛 답장은
지워지므로 **메시지 수는 그대로인데 요청만 늘어난다.** 그리고 잘라내면
`contents.size`가 줄어 캐시가 버려진다 — `SHRUNK`의 정체다.

교차 검증: 재요청 203회 중 `SHRUNK` 36회(17.7%). "마지막 턴만 다시 받는데 그것이
캐시 생성 직후에 걸린 경우"의 이론값 1/5.9 = 16.9%와 거의 일치한다.

### 8.2 무엇을 바꿨나

`CACHE_LAG_ENTRIES = 2`. 캐시 범위를 대화 끝에서 한 교환 뒤로 물린다.

**함께 안 고치면 턴이 두 번 실리는 세 곳이 있다.** 범위만 줄이면 마지막 교환이
캐시와 요청에 중복된다.

```kotlin
val prefix = if (lag > 0) contents.dropLast(lag) else contents
.put("contents", JSONArray().apply { prefix.forEach { put(it) } })  // 올리는 내용
coveredTurns = prefix.size                                          // 범위
fingerprint  = fingerprint(prefix, system)                          // 지문
```

**갱신 주기 보정도 필요하다.** 물린 꼬리는 처음부터 캐시 밖이라 "새로 붙은 것"이
아니다. `PrefixCache.lagEntries`를 저장하고 꼬리를
`drop(coveredTurns + lagEntries)`로 잰다. 이게 없으면 물린 대가를 재생성 횟수로 또 낸다.

### 8.3 무조건 이득은 아니다 — 가드 셋

`prefixCacheLagEntries`가 손해 보는 경우를 막는다.

1. **고쳐 쓴 적 없는 방은 안 물린다.** 이득 0인데 꼬리 값만 물게 할 수 없다.
2. **물려서 `MINIMUM_CACHE_TOKENS`(4,600) 아래로 내려가면 안 물린다.** 캐시가
   아예 안 만들어져 그 방의 캐시를 통째로 잃는 쪽이 훨씬 비싸다.
3. **물릴 만큼 길지 않은 대화는 안 물린다.**

**그리고 표시할 때 줄어든 크기를 본다**(`isRerollShrink`, `REROLL_SHRINK_MAX_ENTRIES = 4`).
줄어드는 이유가 둘인데 대응이 정반대이기 때문이다.

| 원인 | 줄어드는 양 | 대응 |
|---|---|---|
| 답을 다시 받음 | 1~3 엔트리 | 물려서 막는다 |
| 요약이 원문을 접음 (80턴 → 30턴) | **약 100 엔트리** | 막을 수도, 막을 필요도 없다 |

**크기를 안 보면 요약이 50턴에 한 번 반드시 일어나므로 결국 모든 방이 표시된다.**
그러면 고쳐 쓰지 않는 방까지 꼬리 값을 매 요청 물면서 얻는 것이 없다.

씨앗이 출력을 정하지 못하므로, **무작위 씨앗을 넣는 것은 아무 일도 하지 않습니다.**

### 9.2 결론 — 기각

`2082eb2`를 `6ddec38`로 되돌렸습니다. 비용이 0이어도 지웁니다. `nextRequestSeed()`
와 "재요청 때 답이 갈리게 한다"는 주석, 그것을 검사하는 테스트 5개가 남아 있는데
**실제로는 아무 일도 하지 않습니다.** 읽는 사람을 속이므로 없는 것보다 나쁩니다.

`docs/seed-probe.sh`는 남깁니다 — 이 결론의 근거이고, 모델이 바뀌면 다시 잽니다.

### 9.3 우리가 틀렸던 방식

1판 시험은 **"좋아하는 과일 다섯 개를 나열해줘"**를 두 번 물어 같은 답이 나온 것을
"씨앗 없이는 결정적"의 증거로 삼았습니다.

- **답이 뻔한 질문은 씨앗이 무엇이든 같은 답이 나옵니다.** 경우의 수가 없는 질문으로
  무작위성을 재려 했습니다.
- **대조군이 없었습니다.** 씨앗 없이 반복해 보지 않았으므로, 기기에서 재요청 3회가
  갈린 것이 우리 수정 때문인지 원래 그런지 구분할 수 없었습니다.

Codex 검토에서 걸렸습니다. 교훈 둘입니다.

1. 무작위성을 잴 때 답이 뻔한 질문을 쓰지 말 것.
2. **대조군 없이 인과를 주장하지 말 것.**

### 9.4 진짜 원인은 따로 있습니다

사용자가 겪은 "다시 받아도 비슷한 답"은 **결정성 문제가 아니었습니다.**
위 12개 답의 행성 이름을 뽑으면 이렇습니다.

> 루미나-9 · 루미아니스 · 루미아니스 · 크리올리스 · 루미나크라 · 크리올리스
> 루미나-IX · 루미아니스 · 크리스탈리아 · 크리올리스 · 루미나리스-9 · 루미아라

**12개 전부가 `루미-` 아니면 `크리-`로 시작합니다.** 루미아니스가 3번, 크리올리스가
3번 그대로 반복됩니다. 내용도 전부 "결정·프리즘이 빛을 굴절시켜 무지개·오로라가
생기는 행성"입니다. 프롬프트에 **"매번 다른 것을 지어내"**라고 명시했는데도요.

| | 처음 진단 | 실제 |
|---|---|---|
| 증상 | 답이 **똑같이** 온다 | 글자는 다르고 **알맹이가 비슷**하다 |
| 원인 | 씨앗이 고정 | **모델이 한 갈래로 쏠린다** |
| 처방 | 씨앗 바꾸기 | **씨앗으로는 안 풀림** |

긴 역할극이면 문맥과 페르소나가 답을 더 좁히므로 쏠림이 더 심할 것입니다.
**입력을 바꾸는 것**(사용자가 이미 하는 "조금 고쳐서 다시 보내기")이 실제로 듣는
방법이고, 이 데이터가 그것을 뒷받침합니다. 프롬프트에 문구를 넣는 방식은 사용자가
원치 않으므로 제안하지 않습니다.
