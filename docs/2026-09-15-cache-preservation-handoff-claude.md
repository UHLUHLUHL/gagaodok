## 2. 캐시 보존 — 이번 작업의 본체

### 2.1 무엇을 막으려는 것인가

사용자는 **답이 마음에 안 들면 자기 메시지를 눌러 고치고 다시 보낸다.** 글을 안
바꾸고 그냥 보내는 일도 많다. 실측으로 **사용자 메시지 1개당 API 요청 2.17~2.33회**다.

`MessageResendLogic.truncateFrom`이 그 메시지 뒤를 전부 잘라낸다. 그러면
`contents.size`가 줄고, `usablePrefixCache`가 캐시를 통째로 버린다(`SHRUNK`).
버려진 요청은 프롬프트 전체를 **정가(0.75)로** 낸다.

**실측: 다시 받기 215회 중 39회(18%)가 캐시를 깼다.**

이유도 확인했다. 캐시는 평균 **5.4요청마다** 새로 만들어지고, 만들어진 시점까지의
대화를 덮는다. 캐시를 **막 만든 직후**에 다시 받으면 대화가 캐시가 덮는 지점 아래로
잘려 깨진다. 이론상 위험 구간 비율 1/5.4 = 19%, 실측 18%로 일치한다.

### 2.2 물림(`CACHE_LAG_ENTRIES = 2`)

캐시를 만들 때 **마지막 한 교환(사용자 한 마디 + 답 한 번)을 일부러 캐시 밖에 둔다.**
그러면 그 교환을 다시 받아도 캐시가 덮는 부분은 손대지 않는다.

**마지막 턴 재요청은 구조적으로 깨지지 않는다.** 증명:

```
캐시 생성 당시 대화 길이 N  →  coveredTurns = N − 2
지금 길이 M (M ≥ N, 생성 뒤로는 자라기만 한다)
마지막 사용자 메시지를 고치면 → M − 1
SHRUNK 조건: M − 1 ≤ N − 2  ⟺  M ≤ N − 1   그런데 M ≥ N. 성립 불가.
```

두세 턴 전을 고치면 깨질 수 있다. 그건 대화가 실제로 달라지는 지점이라 깨지는
것이 맞다.

**반드시 세 곳을 함께 고쳐야 한다.** 범위만 줄이면 마지막 교환이 캐시와 요청에
**두 번** 실린다.

```kotlin
val prefix = if (lag > 0) contents.dropLast(lag) else contents
.put("contents", JSONArray().apply { prefix.forEach { put(it) } })  // 올리는 내용
coveredTurns = prefix.size                                          // 범위
fingerprint  = fingerprint(prefix, system)                          // 지문
```

그리고 **갱신 주기 보정**이 필요하다. 물린 꼬리는 처음부터 캐시 밖이므로 "새로 붙은
것"이 아니다. `PrefixCache.lagEntries`를 저장하고 꼬리를
`drop(coveredTurns + lagEntries)`로 잰다. 없으면 물린 대가를 재생성 횟수로 또 낸다.

### 2.3 가드 — 아무 방에나 물리면 손해다

물림에도 값이 있다. 마지막 한 교환(435토큰)이 매 요청 정가로 실려 **요청당 0.37원**이다.

```kotlin
internal fun prefixCacheLagEntries(entryCount, laggedPrefixTokens, shrinkProne): Int {
    if (!shrinkProne) return 0                               // 고쳐 쓴 적 없는 방
    if (entryCount <= CACHE_LAG_ENTRIES) return 0            // 접두사가 안 남음
    if (laggedPrefixTokens < MINIMUM_CACHE_TOKENS) return 0  // 캐시가 아예 안 만들어짐
    return CACHE_LAG_ENTRIES
}
```

세 번째가 특히 중요하다. 물리다가 4,600토큰 아래로 내려가면 Gemini가 캐시 생성을
거부해서, **아끼려다 그 방의 캐시를 통째로 잃는다.**

### 2.4 요약과 재요청을 가르는 것 — Codex P2-1 (`7a0f9bb`)

대화가 줄어드는 이유가 **둘인데 대응이 정반대**다.

| 원인 | 줄어드는 양 | 대응 |
|---|---|---|
| 답을 다시 받음 | 1~3 엔트리 | 물려서 막아야 함 |
| **요약이 원문을 접음** (`THRESHOLD_TURNS` 80 → `VERBATIM_WINDOW_TURNS` 30) | **약 100 엔트리** | 막을 수도, 막을 필요도 없음 |

크기를 안 보고 표시하면 **요약은 50턴마다 반드시 일어나므로 결국 모든 방이 표시된다.**
그래서 처음에는 크기 차이로 갈랐는데(`e1f14d3`), **Codex가 그것이 틀렸음을 지적했다.**

> `coveredTurns`는 과거 어느 시점에 만들어진 캐시의 길이이고 `newSize`는 지금 요청의
> 길이다. **기준 시점이 다른 두 수를 빼고 있었다.** 오래된 캐시 길이와 요약 뒤 길이가
> 우연히 비슷하면 정상 요약이 재요청으로 둔갑한다.

실제 `ConversationCompactor.plan`으로 재현했고(회귀 테스트에 박음), 지적이 맞았다.
사용자 32턴에 만든 캐시(63 엔트리)와 1~50턴 요약 후 81턴 요청(원문 61 + preamble 2
= 63 엔트리)이 **차이 0**이 된다.

고친 방식은 Codex 제안대로 **추측하지 않고 부르는 쪽이 알려 주는 것**이다.

```kotlin
val digestCoveredTurns: Int = -1   // PrefixCache. 옛 파일은 -1(모름)

internal fun isRerollShrink(
    cacheDigestCoveredTurns: Int, requestDigestCoveredTurns: Int,
    coveredTurns: Int, newSize: Int
): Boolean {
    if (coveredTurns - newSize < 1) return false            // 줄지 않았다
    if (cacheDigestCoveredTurns >= 0)                       // 요약 범위가 늘었으면 요약이다
        return requestDigestCoveredTurns == cacheDigestCoveredTurns
    return coveredTurns - newSize <= REROLL_SHRINK_MAX_ENTRIES  // 옛 캐시는 크기로만
}
```

호출부는 `ConversationCompactor.Plan.coveredTurns`를 그대로 넘긴다.
차이 0도 재요청에서 뺐다 — 재요청은 최소한 답 하나를 지운다.

### 2.5 표시를 디스크에 남긴다 — 이번 작업 (`79f0b8c`)

**여기가 이번에 가장 중요한 부분이다.** 위 장치가 전부 들어갔는데도 **실사용에서
한 번도 켜지지 않았다.**

물림은 그 방에서 `SHRUNK`을 한 번 겪어야 켜진다(2.3의 첫 가드). 그런데 그 표시를
**메모리에만** 뒀다. 실기기 계측(09-14 16:30 설치 → 09-15 08:04):

```
NOT_BURST  +5        대화 묶음 5번
FIRST      +2        프로세스 최소 2회 재시작
현재 캐시            coveredTurns=139  lagEntries=0   ← 끝까지 안 켜짐
그 사이 다시 받기 12회 중 2회가 캐시를 깼다 (16.7%)
수정 전 비율 17.7%와 사실상 같다
```

**방마다 한 번만 내면 되는 값을 앱을 켤 때마다 다시 내고 있었다.**

`8542b53` 커밋 메시지에 "앱을 다시 켜면 방마다 한 번은 예전처럼 깨진다"고 한계를
적어 두긴 했다. **하루에 몇 번이나 그럴지를 계산하지 않은 것이 실수다.**

고친 내용:

```kotlin
// AIService.kt
internal val shrinkProneFile: File by lazy {
    File(File(appContext.filesDir, "KakaoSapiens").apply { mkdirs() }, "shrink_prone_rooms.json")
}
internal val shrinkProneRooms: MutableSet<String> by lazy {
    ConcurrentHashMap.newKeySet<String>().apply { addAll(readShrinkProneRooms(shrinkProneFile)) }
}

// AIServicePrefixCache.kt
internal fun AIService.markShrinkProne(key: String) {
    if (!shrinkProneRooms.add(key)) return   // 이미 적혀 있으면 파일을 안 건드림
    scope.launch { writeShrinkProneRooms(shrinkProneFile, shrinkProneRooms.toSet()) }
}
```

설계에서 신경 쓴 셋:

1. **못 읽으면 빈 것으로 친다.** 캐시를 아끼려는 표시일 뿐인데 여기서 예외가 나가면
   그 방은 대화 자체가 막힌다.
2. **쓰다 실패해도 조용히 넘어간다.** 다음 실행에서 한 번 더 겪을 뿐이다.
3. **쓰는 시점에 목록을 다시 모은다.** 미리 찍어 두면 두 방이 거의 같이 표시됐을 때
   늦게 도착한 쓰기가 옛 목록으로 덮어써 한쪽이 사라진다.

읽기는 앱 시작 시 한 번, 쓰기는 **방마다 평생 한 번**이다.

## 3. 새로 드러난 비용 구조

### 3.1 캐시 생성은 청구되지 않는 것으로 보인다 — **9.2에서 확정됨**

> **이 절은 추정 단계의 기록이다.** 결론은 맞았지만 근거(사용자가 알려 준 "약 260원")가
> 약했고, 여기서 역산한 환율 1,251원은 **틀렸다**(실제 1,383원, 9.4 참조).
> 확정 근거는 9장에 있다. 아래는 그 전에 어떻게 추론했는지의 기록으로 남긴다.

**오래 막혀 있던 질문의 유력한 답이다.** 사용자가 9턴 쓰고 **약 260원**이 빠졌다고
알려 왔다. 같은 구간 장부 증분으로 계산하면:

| 항목 | 금액 (환율 1,420) |
|---|---|
| 비캐시 입력 190,293토큰 | 203원 |
| 캐시 읽기 469,170토큰 | 50원 |
| 출력 7,981토큰 | 42원 |
| **소계 (생성료 제외)** | **295원** |
| 캐시 생성 187,124토큰 | +199원 |
| 합계 (생성 과금 가정) | **494원** |

- 생성 과금 가정 494원은 관측 260원과 **1.9배** 차이 — 맞지 않는다.
- 생성 비과금 295원은 12% 차이인데, **환율 1,251원을 넣으면 259.8원으로 정확히 맞는다.**

**확정은 아니다**(관측 1회, "약 260원"). Cloud Billing → 보고서 → 그룹화 기준 SKU에서
입력 토큰 수량을 보면 끝난다.

> **이것이 맞다면 지금까지 우리가 쓴 비용 숫자는 전부 약 40% 과대평가다.**
> `TokenUsageStore.costUSD`가 "확실하지 않을 때는 비싼 쪽으로" 원칙으로 생성 토큰을
> 입력 단가로 계산하기 때문이다. 건당 18.25원이 아니라 약 11원이다.

### 3.2 캐시가 실제로 얼마나 아끼고 있나

> **환율이 1,251이 아니라 1,383이다**(9.4). 아래 원화 금액은 그만큼 낮게 잡혀 있다.
> **배수(3.3배 / 5.1배)는 환율과 무관하므로 그대로 유효하다.**

단가는 10배 차이(0.75 vs 0.075)지만 실제 절감은 그만큼 나오지 않는다.
run-9 416요청 실측, 생성 비과금 가정:

| | 총액 | 건당 | 절감 |
|---|---|---|---|
| 캐시가 아예 없었다면 | 11,956원 | 28.7원 | — |
| **실제** | **3,587원** | **8.6원** | **3.3배** |
| 빗나감이 0이었다면 | 2,338원 | 5.6원 | 5.1배 |

**10배가 안 되는 이유는 둘이다.**

1. **적중해도 전부 싸지지 않는다.** 요청 28,857토큰 중 캐시가 덮는 것은 27,379,
   **꼬리 1,478토큰은 늘 정가**다. 게다가 출력은 캐시와 무관하게 $3.75다.
   그래서 **이론상 한계가 5.1배**다.
2. **캐시가 깨진다.** 5.1배까지 갈 수 있는데 3.3배에 머문다.

못 받은 절감분 **1,248원**의 내역:

| 빗나간 이유 | 건수 | 값 |
|---|---|---|
| **`SHRUNK`** | **39** | **902원 (채팅 비용의 25%)** |
| 만료·묶음 첫 요청 등 | 15 | 346원 |

### 3.3 물림 영속화의 손익

| | |
|---|---|
| `SHRUNK` 39회가 부른 값 | +905원 |
| 물림을 항상 켜는 대가 (416요청 × 0.37원) | −153원 |

**남는 손해 경우**: 예전에 한 번 다시 받고 그 뒤로 평생 안 하는 방은 표시가 영구히

만료를 붙일 수 있다.

## 4. 씨앗 기각 (`6ddec38`) — 우리가 틀렸던 방식

`2082eb2`에서 "같은 대화를 다시 보내면 답이 그대로"라며 요청마다 무작위 씨앗을
넣었다. **실측으로 기각하고 되돌렸다.**

시험: `docs/seed-probe.sh`, `gemini-3.8-flash`, 호출 12회, 열린 질문.

| 구간 | 조건 | 서로 다른 답 |
|---|---|---|
| A | seed 없이 5회 | **5 / 5** |
| B | seed 11·22·33·44·55 | 5 / 5 |
| C | **같은 seed 77로 2회** | **서로 다름** |

**C가 결정적이다.** 씨앗을 고정해도 출력이 고정되지 않는다. 씨앗은 사실상 무시된다.

### 9.2 **확정** — 캐시 생성은 청구되지 않는다

청구되는 SKU는 넷뿐이다.

```
input token count · cached input token count · output token count
cached content storage token hours
```

3.8·3.7 양쪽 모두 **캐시 생성 항목이 없다.**

**이 판정은 금액이 아니라 개수로 했으므로 필터의 영향을 받지 않는다.**

| | 우리 장부 | 청구서 | 일치 |
|---|---|---|---|
| 비캐시 입력 | 6,314,689 | 6,242,745 | **99%** |
| 캐시 읽기 | 35,447,421 | 35,296,876 | **100%** |
| 출력 | 341,978 | 339,611 | **99%** |
| **캐시 생성** | **7,946,727** | **항목 없음** | — |

생성이 입력 SKU에 섞였다면 입력이 **14,261,416**이어야 했다. 실제는 6,242,745다.
2.3배 차이라 필터나 기간 어긋남으로 설명되지 않는다.

세 항목이 99~100%로 맞는다는 것은 **장부와 청구서가 같은 것을 세고 있다**는 뜻이기도

### 9.3 **확정** — 보관료는 청구된다. 그리고 우리 장부가 35% 적게 센다

`cached content storage token hours gemini 3.8 flash` 1,539,742시간 → ₩1,065.
단가 $0.50/M·시간이 정확히 맞는다.

**그런데 우리 장부는 1,006,906시간으로 65%밖에 안 된다.** 같은 모델·같은 기간인데
다른 세 항목은 99~100%로 맞으므로 집계 결함이다. **원인을 찾아 `f45e307`에서 고쳤다.**

**결함 둘이 서로를 가리고 있었다.**

1. **단위가 틀렸다.** `faa7429`에서 `× tokenCount`가 빠졌다.

   ```kotlin
   // 이전 (단위는 맞고 과대추정)
   tokenHours = cachedTokens * (CACHE_TTL_SECONDS / 3600.0)
   // 이후 — 토큰 수가 빠졌다
   val livedHours = (now - createdAtMillis) / 3_600_000.0
   usage.recordCacheLeaseEnd(roomId, model, it.tokenCount, livedHours)
   ```

   받는 쪽은 `tokens`를 **쓰지 않고** 두 번째 인자를 그대로 저장했다. 이름은
   `tokenHours`인데 들어오는 것은 `hours`였다. 캐시 하나가 약 27,000토큰이므로
   **약 27,000배 작게** 적혔다.

2. **버리는 캐시는 정산되지 않았다.** 정산은 `refreshPrefixCache`가 교체할 때
   한 곳에서만 일어났는데, run-9의 캐시 생성 74회 중 그 경로는 **11회(15%)**뿐이다.
   나머지 63회(SHRUNK 39·EXPIRED 15·FIRST 9)는 `dropCache`로 버려졌다.

장부가 그럼에도 65%나 되는 것은 현재 값 대부분이 `faa7429` **이전**에 쌓인
(단위는 맞고 과대추정이던) 몫이기 때문이다. **또 두 오류가 상쇄된 사례다.**

고친 내용: 계산을 `cacheLeaseTokenHours` 한 곳으로 모으고, `dropCache`에서도 정산하며,
`recordCacheLeaseEnd`의 인자를 **하나(토큰·시간)로 줄였다** — 둘을 받으면서 하나를
안 쓰는 구조가 이 버그를 불렀다.

**아직 안 맞는 부분**: 앱이 꺼진 사이 만료된 캐시는 여전히 정산되지 않는다.
시작할 때 만료된 것을 걸러 내며 버리는데 거기서는 적지 않는다.

**다음 측정은 새 run부터 비교할 것.** 기존 값에 옛 단위가 섞여 있다.

## 10. 코덱스 검토 반영 — 물림이 실사용에서 안 켜지던 결함 (`RerollShrinkFlowTest`)

코덱스가 `f8c0084`의 소스를 다시 컴파일해 재현한 결과를 보내 왔다. **지적이
맞았고, 관찰로 넘길 문제가 아니라 코드 결함이었다.**

### 10.1 확정 — 재요청은 길이를 줄이지 않고 되돌린다

캐시는 답변이 저장되기 **전**, 방금 보낸 요청의 `contents`로 만들어진다
(`AIServiceConversation.kt`의 `refreshPrefixCache` 호출부. 주석에도 "방금 실제로
보낸 contents를 그대로 올립니다"라고 적혀 있다). 그래서 `coveredTurns`는
"사용자 메시지까지"의 길이다.

```
캐시 생성 63  →  답변 저장 64  →  답을 다시 받음 63
```

`usablePrefixCache`는 `contents.size <= cache.coveredTurns`로 `SHRUNK`을 잡으므로
**같은 길이도 걸린다.** 그런데 `isRerollShrink`는 `coveredTurns - newSize < 1`에서
즉시 `false`였다. **차이가 0이라 재요청으로 판정되지 않았고 `markShrinkProne`이
호출되지 않았다.**

`ConversationTurn.from`이 AI 응답의 말풍선 여럿을 한 턴으로 묶으므로, 재요청은
언제나 정확히 **1 엔트리**만 지운다. 네 가지 재요청 전부 63→63이다.

### 10.2 재현 — 실제 경로를 이어 붙인 회귀 검사

`RerollShrinkFlowTest`가 `MessageResendLogic.truncateFrom` → `ConversationTurn.from`
→ `isRerollShrink`를 실제 production 함수로 잇는다. `buildGeminiContents`는
`AIService` 확장이라 단위 검사에서 부를 수 없어 `ConversationTurn.from(...).size`로
대신했다 — 오류 턴과 빈 파트만 빼면 1:1이므로 이 본문들에서는 같다. **이 한 가지는
근사이고, 나머지는 실제 함수다.**

| 경우 | 캐시 길이 → 재요청 길이 | 고치기 전 | 고친 뒤 |
|---|---|---|---|
| 일반 재생성 | 63 → 63 | 표시 안 됨 ❌ | 표시됨 ✅ |
| 같은 문구로 재전송 | 63 → 63 | 표시 안 됨 ❌ | 표시됨 ✅ |
| 일부 수정 재전송 | 63 → 63 | 표시 안 됨 ❌ | 표시됨 ✅ |
| 전면 수정 재전송 | 63 → 63 | 표시 안 됨 ❌ | 표시됨 ✅ |
| 첨부 전용 재전송 | 63 → 63 | 표시 안 됨 ❌ | 표시됨 ✅ |
| 말풍선 3개 답 재생성 | 63 → 63 | 표시 안 됨 ❌ | 표시됨 ✅ |
| **과거 메시지 수정** | 63 → 59 | 표시됨 ✅ | 표시됨 ✅ |

**길이 단언(63→63)은 고치기 전후로 같다.** 바뀐 것은 판정뿐이므로, 이 표는 수정이
길이 계산이 아니라 경계 조건만 건드렸다는 증거이기도 하다.

고치기 전 이 검사는 `assertFalse`로 7/7 통과했고(결함을 기록한 상태), 조건을
`< 0`으로 바꾸자 정확히 그 여섯이 뒤집혔다.

### 10.3 왜 기존 단위 검사가 놓쳤나

`PrefixCacheLagTest`의 `같은 흐름에서 답을 다시 받으면 표시된다`는
`coveredTurns = 63, newSize = 62`를 **손으로 넣고 있었다.** 그 62가 어디서 오는지는
아무 검사도 하지 않았다. 게다가 `줄지 않았으면 답을 다시 받은 것이 아니다`가
차이 0을 `false`로 **못박아 두어**, 결함을 정답으로 고정하고 있었다.

**교훈**: 값을 손으로 넣는 검사는 그 값이 실제로 나오는지를 검사하지 않는다.
경계 조건은 실제 경로를 이어서 잡아야 한다.

### 10.4 수정

`isRerollShrink`의 `coveredTurns - newSize < 1` → `< 0`. 부르는 쪽이
`contents.size <= coveredTurns`일 때만 들어오므로 음수는 나오지 않지만, 조건이
바뀌어도 무너지지 않게 남겼다.

**요약 오인 위험은 없다.** 차이가 0이어도 `digestCoveredTurns`가 다르면 (요약이
전진했으면) 그 앞에서 `false`가 된다. 그 경우를 `길이가 그대로여도 요약이 돌았으면
답을 다시 받은 것이 아니다`로 따로 고정했다.

**남는 오탐 하나**: 네트워크 실패 뒤 같은 요청을 다시 보내면 길이가 같아 재요청으로
잡힌다. 물림 비용은 요청당 0.37원이고 손익분기가 1.58%이므로 받아들일 만하다.
그리고 사실상 같은 현상이다.

### 10.5 조건부 확정 — 680턴 비동기 순서

680턴에서 `refreshPrefixCache`(옛 요약 기준)와 `updatePhoneMemory`(새 요약 저장)가
각각 `scope.launch`로 돈다. **설치 시점의 세대 검사는 없다.** `refreshingRooms`는
같은 방의 동시 갱신만 막지, 늦게 끝난 갱신이 새 요약 뒤에 설치되는 것은 막지 않는다.

다만 **잘못 쓰이지는 않는다.** 그 캐시는 `digestCoveredTurns = 600`으로 박히고,
다음 요청은 650 기준이라 `usablePrefixCache`에서 길이와 지문 양쪽으로 걸러진다.
`isRerollShrink`도 요약이 전진했으므로 `false`다 — **잘못된 shrink-prone 표시도
생기지 않는다.**

남는 것은 낭비뿐이다. 쓰이지 않을 캐시를 한 번 만들고, 다음 요청까지 보관료가
붙는다. 생성은 청구되지 않으므로(9.2) 비용은 보관료뿐이고, 27,000토큰 × 수 분이면
원 단위다. **고칠 값어치가 있는지는 미판정.** 세대 검사를 넣는다면
`digestCoveredTurns`를 설치 직전에 다시 읽어 달라진 경우 올린 캐시를 버리는
방식이 될 것이다.

### 10.6 확정 — "18%"가 두 가지로 쓰이고 있었다

이 문서 안에 **분모가 다른 18%가 둘** 있다. 우연히 값이 같아 더 위험하다.

| 표기 | 값 | 분모 | 뜻 |
|---|---|---|---|
| 3장 | 18.1% | 39 / **재요청 215회** | 재요청이 캐시를 깰 확률 |
| 9.9장 | 18% | 2,868원 / **청구서 16,199원** | 비용에서 차지하는 몫 |
| 4장 | 9.4% | 39 / **전체 CHAT 416요청** | 요청당 발생률 |

요약표(19행)의 "`SHRUNK`이 폰 청구서의 18%"는 둘을 섞은 표현이다. **앞으로는
세 가지를 이름으로 구분한다.**

- `재요청_깨짐률` = 재요청 때문에 생긴 `SHRUNK` / 캐시가 있던 적격 재요청
- `요청당_SHRUNK률` = `SHRUNK` / 전체 CHAT 요청
- `비용비중` = 그 값 / 청구 총액

**680·730·780턴의 정상 압축으로 생긴 캐시 폐기는 세 지표 어디에도 넣지 않는다.**
그것은 재요청 실패가 아니다. `CacheDropReason`만으로는 갈라지지 않으므로
(둘 다 `SHRUNK`), 압축 전환이 일어난 요청을 따로 표시해야 한다. **현재 계측에는
그 구분이 없다.** 미구현.

### 10.7 표본 크기 — "한 자릿수면 성공"은 성급하다

기존 39/215 = 18.1%의 95% 구간은 약 13.6~23.8%다. 새 결과가 7/80이면 8.8%이고

판정은 이렇게 한다.

- 감소 **방향**이 나타났는가
- 적격 재요청이 실제로 몇 건인가 (분모가 작으면 비율은 의미가 없다)

- 남은 `SHRUNK`이 만료·요약·과거 편집·동시성 중 무엇인가

## 11. 보정한 관찰 계획

10장의 결함을 고치기 전까지, **물림은 실사용에서 한 번도 켜질 수 없었다.** 9월
14~15일에 설치한 빌드 전부가 여기에 해당한다. 관찰 계획도 그에 맞춰 다시 세운다.

### 11.1 ① 다음 재요청 한 번 — 두 가지를 동시에 본다

예전에는 이것을 "영속화 검사"라고만 적었다. **틀렸다.** 영속화 함수에 도달하기
전의 판정(10.1)에서 막히고 있었으므로, 이 검사는 **판정과 영속화를 함께** 본다.

사전조건 — 하나라도 어긋나면 결과를 해석할 수 없다.

| 조건 | 왜 |
|---|---|
| 그 방에 만료되지 않은 `lagEntries=0` 캐시가 있다 | 없으면 `SHRUNK` 자체가 안 난다 |
| 접두사가 `MINIMUM_CACHE_TOKENS`(4,600) 이상 | 아래면 캐시가 아예 안 만들어진다 |
| 재요청 사이에 모델·페르소나·요약이 그대로 | 바뀌면 다른 사유로 폐기된다 |
| 파일 확인은 비동기 쓰기가 끝난 뒤 | `markShrinkProne`은 `scope.launch`로 쓴다 |

판정.

| 관찰 | 통과 | 실패 시 해석 |
|---|---|---|
| `SHRUNK` 기록 | 있어야 함 | 없으면 캐시가 애초에 없었다 — 사전조건 미충족 |
| `shrink_prone_rooms.json`에 `roomId\|model` | 있어야 함 | **없는데 `SHRUNK`은 있다 → 판정 실패(10.1 재발) 또는 영속화 실패** |
| 앱 재시작 뒤에도 파일 유지 | 유지 | 사라지면 영속화 실패 |
| 다음 캐시의 `lagEntries` | **2** | 0이면 `prefixCacheLagEntries`의 다른 조건에 걸린 것 |
| 물린 접두사와 원래 접두사 | 앞부분 일치 | 어긋나면 지문 검사에서 탈락한다 |

**두 실패를 가르는 법**: `SHRUNK`은 있는데 파일이 없으면, 같은 방에서 한 번 더
재요청해 본다. 판정 실패라면 몇 번을 해도 파일이 안 생긴다. 영속화 실패라면
메모리에는 남아 있으므로 그 세션 안에서 다음 캐시가 `lagEntries=2`로 나온다.

### 11.2 ② 680턴 압축 — 합격 기준을 낮춘다

예전 기준("`SHRUNK`이 반드시 기록되고 새 캐시가 만들어져야 통과")은 **너무 엄격했다.**
캐시가 이미 만료됐거나, 다른 사유로 폐기되거나, burst·최소 토큰 조건 때문에 새
캐시가 바로 안 생길 수 있다. 전부 정상이다.

| | 관찰 |
|---|---|
| **필수** | 요약 적용 범위가 600 → 650으로 정확히 전진 |
| **필수** | 새 요약 기준 요청에서 옛 요약(1~600) 캐시 사용 **0건** |
| **필수** | 정상 압축을 재요청으로 오인해 새 shrink-prone 표시를 만들지 **않음** |
| 조건부 | 활성 캐시가 있었다면 적절한 사유로 폐기 (`SHRUNK`/`FINGERPRINT_CHANGED` 모두 정상) |
| 조건부 | 생성 조건을 채웠다면 새 요약 기준 캐시 생성 |
| 조건부 | 기존 shrink-prone 표시가 유지됨 |
| **실패** | `lagEntries` 여부와 무관하게 옛 요약 캐시를 계속 사용 |
| **실패** | 정상 압축이 shrink-prone 표시를 새로 만듦 |

비동기 순서(10.5)도 함께 본다 — 680 응답 직후 만들어진 캐시의
`digestCoveredTurns`가 600인지 650인지. 600이면 늦게 설치된 것이고, 다음 요청에서
즉시 버려져야 한다.

### 11.3 ③ 750~800턴 효과 측정 — 분모를 못박는다

10.6의 세 이름을 그대로 쓴다. **주 지표는 `재요청_깨짐률`이다.**

```
재요청_깨짐률 = 재요청 때문에 생긴 SHRUNK / 캐시가 있던 적격 재요청
```

함께 기록할 것.

- 캐시 미적중 사유별 요청 수 (`CacheDropReason` 분포)
- 물림 활성 전후의 **비캐시 입력 토큰**
- 캐시 읽기 · 일반 입력 · 출력 · 보관 token-hours
- 사용자 1턴당 비용, 재요청 1건당 비용
- shrink-prone이 켜진 방과 안 켜진 방을 **분리**

800턴 자체는 임계점이 아니다. 다만 680·730·780의 압축 셋과 그 뒤 안정 구간까지
들어온다. **억지로 턴을 채우지 않는다** — 평소 패턴이 아니면 측정이 실제를 안 닮는다.

### 11.4 ④ 청구서 대조 — 총액만 보지 않는다

총 사용량이 달라지면 총액으로는 기능 효과를 가릴 수 없다. 맞출 조건.

- 같은 모델, 같은 SKU 단가
- **새 장부 run 시작 이후만** — 기존 token-hours에는 단위 오류가 섞여 있다(9.3)
- 사용자 턴 수와 재요청 수를 함께 기록
- 사용자 1턴당 / 재요청 1건당 **비캐시 입력** 비용
- 캐시 읽기 대 일반 입력 토큰 비율
- 보관 token-hours를 장부와 SKU **수량**으로 대조
- 채팅 · 기억 요약 · 출력 비용 분리
- 환율 효과와 실제 토큰 감소 분리
- 청구 지연이 있으면 장부와 **같은 완료 기간**만 대조

**월 5,100원 / 15%는 추정치다.** 9.9의 계산은 물림이 실제로 켜진 적 없는 상태에서
`SHRUNK` 횟수만으로 뽑은 값이다.
