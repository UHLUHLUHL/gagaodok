# 가가오독 안드로이드 판

맥 판(`../Sources/KakaoSapiens`)과 같은 앱입니다. 카카오톡처럼 생긴 껍데기 안에서
AI와 수학을 공부하거나(멘토 모드) 캐릭터와 대화합니다(챗봇 모드).

계획과 배경은 [ANDROID_PLAN.md](../ANDROID_PLAN.md)에 있습니다. 이 문서는 **지금 상태**만 적습니다.

---

## 빌드

```bash
source ~/Library/Android/sdk/env.sh   # JAVA_HOME, ANDROID_HOME, PATH
./gradlew assembleRelease
```

산출물: `app/build/outputs/apk/release/app-release.apk` (약 5.2MB)

시험만 돌릴 때는 `./gradlew testDebugUnitTest`입니다.

| 항목 | 값 |
|---|---|
| minSdk | 26 (Android 8.0) |
| targetSdk | 35 (Android 15) |
| 패키지 | `com.sapiens.gagaodok` |
| JDK | 17 |
| 서명 | **디버그 키** (아래 참고) |

### 서명에 대해

릴리스 APK를 디버그 키로 서명합니다. 혼자 쓰기에는 그것으로 충분하고,
키 저장소는 잃어버리면 같은 앱으로 업데이트할 수 없게 되는 물건이라
필요해질 때 만드는 편이 낫습니다.

스토어에 올리거나 남에게 배포하려면 키 저장소를 만들고
`app/build.gradle.kts`에 `signingConfigs { create("release") { ... } }`를 추가하면 됩니다.
릴리스 설정이 이미 `signingConfigs.findByName("release") ?: debug`로 되어 있어
그것만 채우면 자동으로 그 키를 씁니다.

## 맥 판과 다른 점

### 화면 구조

맥 판의 **왼쪽 세로 레일을 그대로 옮기지 않았습니다.** 폭 48dp를 통째로 먹는데
360dp 폰에서 그건 화면의 13%입니다. 카카오톡 모바일이 레일 대신 아래 탭바를
쓰는 이유가 그것입니다. 아래 탭 3개(친구·채팅·설정)로 바꿨습니다.

창 여러 개 대신 화면 전환입니다. 대화방은 오른쪽에서 밀려 들어오고 뒤로가기로 나갑니다.

### 뺀 것

- **창 투명도 슬라이더** — 창이라는 개념이 없습니다
- **여러 창 띄우기** — 화면 전환으로 대신합니다
- **마우스 올림(hover)** — 눌림 효과와 길게 누르기로 바뀌었습니다.
  맥 판에서 마우스를 올려야 나오던 수정·복사 버튼과 오른쪽 클릭 메뉴는
  말풍선을 길게 누르면 나오는 시트 하나로 모았습니다.

### 색과 크기 — 이제 실측값입니다

첫 판은 맥 판에서 색을 옮기고 크기는 짐작으로 정했습니다.
지금은 **안드로이드 카카오톡 실기기 캡처를 화소 단위로 재서** 맞췄습니다.
재는 방법과 원본 화소값은 [MEASURED.md](MEASURED.md)에 있습니다.

**색도 데스크톱과 다릅니다.** 옮겨 써도 되는 줄 알았는데 아니었습니다.

| 자리 | 맥(데스크톱) | 모바일 |
|---|---|---|
| 대화방 배경 | `#B2C7D9` | `#ABC1D1` |
| 내 말풍선 | `#FEE500` | `#FFEB33` |
| 보낸이 이름 | 흐린 회색 | `#191919` (본문과 같은 검정) |

**프로필 사진은 둥근 사각형이 아니라 초타원입니다.** 채팅 목록의 180×180 화소
아바타에서 180개 행의 폭을 재어 맞춘 지수가 2.70입니다(잔차 0.0001,
타원 2.0은 0.0203, 4.0은 0.0349). 둘은 크기가 같아도 나란히 놓으면 계속 달라 보입니다.

`ui/KakaoMetrics.kt`와 `ui/theme/Type.kt`에는 값마다 잰 화소값을 함께 적어 두었고,
아직 못 잰 것은 **(짐작)**이라고 표시했습니다. 나중에 실측값으로 오해받아
지워지지 않게 하려는 것입니다.

아이콘은 **도형만** 가져왔습니다. 맥 판이 실측으로 뽑은 곡선(초타원 어깨, 타원 말풍선,
돋보기 획 굵기)은 비율이라 그대로 쓸 수 있고, 크기는 실측해 정했습니다.

### 원조와 일부러 다르게 둔 것

- **대화방 상단 바에 모델·모드 줄을 두지 않습니다.** 원조는 한 줄(뒤로·이름·돋보기·메뉴)
  이라 그 구성을 따랐습니다. 지금 쓰는 모델과 모드는 이름을 누르면 나오는 메뉴에
  ✓로 표시되므로 정보는 그대로 있습니다.
- **입력바의 `#`과 음성 단추는 그리지 않습니다.** 우리 앱에 해당 기능이 없습니다.
  모양·치수·색은 원조를 그대로 따르고 단추 수만 우리 기능(첨부·필드·보내기)에 맞췄습니다.
  눌러도 아무 일이 없는 단추를 모양 때문에 넣지 않기 위해서입니다.

## 저장 형식은 맥 판과 같습니다

`files/KakaoSapiens/` 아래 파일 이름과 JSON 형식을 맥 판과 똑같이 맞췄습니다.
맥에서 쓰던 기록을 복사해 넣으면 그대로 읽힙니다.

그 호환을 지키느라 두 가지를 흉내 냅니다. 둘 다 `model/Codec.kt`에 모여 있습니다.

- **날짜**: Swift `Codable`은 2001-01-01을 0으로 삼는 실수 초입니다.
  유닉스 기준시와 978,307,200초 차이라, 모르고 그냥 쓰면 31년이 어긋납니다.
- **UUID**: Swift는 대문자 하이픈 형식으로 씁니다.

## 안드로이드에서 새로 생긴 것

- **ViewModel** — 화면을 돌리거나 앱이 잠시 뒤로 밀렸다 돌아오면 뷰가 새로 만들어집니다.
  맥 판처럼 뷰 안에 상태를 두면 그때 받던 답변이 통째로 사라집니다.
- **EncryptedSharedPreferences** — 맥 판의 키체인 자리입니다.
  **APK는 뜯어보면 안이 다 보이므로 키를 코드에 넣지 않습니다.** 사용자가 설정에서 직접 넣습니다.
- **Pretendard 번들** — 맥에는 시스템에 깔려 있지만 여기는 없습니다.
  `assets/fonts`에 세 굵기(4.5MB)를 넣고, 네이티브와 수식 웹뷰가 **같은 파일**을 씁니다.
  양쪽에 따로 두면 같은 글꼴이 두 벌 들어갑니다.
- **화면 가장자리 처리** — targetSdk 35는 앱이 상태 표시줄과 제스처 바 아래까지 그립니다.
  상단 바는 `statusBars`만큼 내리고, 탭바·입력창은 `navigationBars`와 `ime`만큼 올립니다.

## 겪은 함정

나중에 같은 자리에서 헤매지 않도록 적어 둡니다.

**1. 웹뷰가 알려주는 높이는 CSS 화소다.**
`container.scrollHeight`를 기기 화소로 알고 밀도(2.75)로 나눴더니 말풍선 높이가
실제의 1/2.75가 되어 글이 잘렸습니다. 수식은 그 좁은 틈으로 잘려 **점처럼** 보였는데,
글자가 작아진 게 아니라 잘린 것이었습니다. 지금은 JS에서
`scrollHeight * devicePixelRatio`로 기기 화소를 만들어 보냅니다.
이 웹뷰의 dpr(2.625)과 안드로이드 밀도(2.75)가 다르기 때문에 둘 중 하나로 통일해야 합니다.

**2. "이미 그렸다"는 기록은 준비 여부와 함께 들고 다녀야 한다.**
`AndroidView`의 update는 페이지가 뜨기 전에도 불립니다. 그때 그린 것으로 치고 기록하면
정작 준비된 뒤에 그리지 않아 말풍선이 통째로 빕니다. `BubbleWebState`가 그 둘을 함께 봅니다.

**3. 에뮬레이터(소프트웨어 GPU)의 상태 표시줄은 잘려 보인다.**
시계가 반쯤 잘려 보여서 앱이 덮은 줄 알았는데, 홈 화면에서도 똑같았습니다.
앱 문제가 아닙니다. 재기 전에 홈 화면과 비교하세요.

**4. 커서를 넣는 것만으로는 키보드가 올라오지 않는다.**
`focusRequester.requestFocus()`에 `LocalSoftwareKeyboardController.show()`를 함께 불러야 합니다.

**5. R8은 Tink가 참조하는 errorprone 애너테이션을 못 찾는다.**
`-dontwarn com.google.errorprone.annotations.**`가 필요합니다. 동작에는 영향이 없습니다.

**6. 글자를 재려면 기기의 글꼴 배율부터 맞춰야 한다.**
같은 글자를 재니 우리 것이 원조보다 8.5% 컸습니다. 글자 크기를 줄이려다,
한 줄짜리 말풍선 높이로 배율을 갈라내니 사용자 기기가 0.91이었습니다.
그걸 걷어내면 원조 본문은 14.7sp라 지금 값(15sp)이 맞았습니다.
대조 전에 `adb shell settings put system font_scale 0.94`로 맞춰 두세요.
길이는 밀도만 알면 되지만 글자는 배율이 하나 더 끼어 있습니다.

**7. 좌우로 뒤집은 도형은 호의 회전 방향도 뒤집어야 한다.**
말풍선 꼬리를 오른쪽으로 옮기며 시작 각도만 옮기고 회전 방향을 그대로 뒀더니,
모서리마다 호가 반대편에서 시작해 직선이 가로질렀습니다. 내 말풍선만 찢어져 보였습니다.

**8. 꼬리는 뿔이 아니라 골이 만든다.**
뿔이 몸통 밖으로 나가는 거리는 반지름의 0.14배로 작습니다. 원조가 깃발처럼
뚜렷한 것은 뿔과 윗변 사이가 깊게 파여서입니다. 골 없이 볼록하게만 부풀렸더니
꼬리를 그려 넣고도 화면에서는 "꼬리가 없다"로 읽혔습니다.

## 아직 확인하지 못한 것

- **실제 API 키로 하는 종단 대화.** Gemini SSE 스트리밍, 명시적 캐시, 구간 요약은
  코드가 다 들어가 있고 키가 없을 때의 오류 경로까지 화면에서 확인했지만,
  키가 있어야 하는 정상 경로는 돌려보지 않았습니다. 남의 키로 요금을 쓸 수 없어서입니다.
- **그래프 그림.** 태그를 읽고 그릴 수 있는 식인지 가리는 부분은 시험이 있지만,
  실제로 비트맵을 그리는 부분은 답변에 `[GRAPH: ...]`가 들어와야 돌아갑니다.
- **수식 말풍선의 폭.** 지금은 최대 폭을 꽉 채웁니다. 짧은 수식에도 그래서
  말풍선이 넓습니다. 카카오톡 말풍선은 내용에 맞게 줄어드는데, 웹뷰는 자기 폭을
  먼저 정해야 높이를 알 수 있어 그렇게 하려면 한 번 더 재는 과정이 필요합니다.
- **말풍선 최대 폭.** 받은 캡처에는 줄바꿈까지 간 말풍선이 없어 못 쟀습니다.
  지금 값(화면 폭의 0.68)은 짐작입니다. 긴 답변이 담긴 화면을 한 장 받으면 확정합니다.
- **다크 모드의 모바일 값.** 라이트만 실측했습니다. 다크는 맥 판에서 옮긴 값이고,
  대화방 시각 색만 라이트 실측값을 어두운 바탕으로 옮겨 잡았습니다(짐작).
  길게 누르기 메뉴와 수정 바의 다크 값도 마찬가지로 못 쟀습니다.
- **수정 필드가 최대 몇 줄까지 자라는지.** 받은 캡처의 다섯 줄짜리는 상한에 닿지 않은
  자연스러운 높이였습니다. 지금 상한(여섯 줄)은 짐작입니다.
- **접힌 수정 필드에 보이는 줄.** 원조는 마지막 줄, 우리는 첫 줄입니다.
  `BasicTextField`가 스크롤 위치를 밖에서 잡을 손잡이를 안 내줍니다. 자세한 것은
  `MEASURED.md`의 "아직 원조와 다른 것"에 적었습니다.
- **프로필 화면의 치수.** 카카오톡 프로필 화면 캡처를 아직 못 받았습니다.
  아바타 크기(112dp), 글자 크기, 아래 단추 줄의 높이, 사진이 없을 때의 바탕색(#3B4650)이
  모두 짐작입니다. 사진 위를 덮는 어둡기(검정 55%)도 그렇습니다.
- **메뉴 카드의 체크 표시.** 지금 고른 모드·모델에 붙는 체크는 말투 표시와 같은
  카카오 금색으로 뒀습니다. 원조에 같은 자리가 없어 재지 못했습니다.
- **말투 조사·미리보기의 실제 동작.** 진행 표시와 미리보기 말풍선은 화면에서
  확인했지만, 실제로 답이 오는 경로는 키가 있어야 합니다. 아래 첫 항목과 같은 이유입니다.
- **실기기 실행.** 화면 대조는 사용자가 보낸 실기기 캡처로 했지만, 고친 뒤 실행은
  에뮬레이터(Pixel 6, Android 15)에서만 했습니다. 다만 에뮬레이터를 사용자 기기와
  같은 자(1440×2936, 밀도 3.75, 글꼴 배율 1.0)로 맞추고 쟀습니다.
  **글꼴 배율은 1.3에서 0.94 → 1.0으로 바로잡았습니다.** 이유는 `MEASURED.md`에 있습니다.

## API 요금 — 1.4에서 고친 것

사용자가 "앱 안의 금액이 실제보다 적은 것 같다"고 했고, 코드를 보니 맞았습니다.
숨어 있던 곳들입니다.

**하나. 대화 답변 말고는 아무것도 안 적혔습니다.**
`postGemini`로 나가던 다섯 가지 — 구간 요약, 말투 조사, 말투 분석, 다듬기,
미리보기 — 가 장부에 한 줄도 안 남았습니다. 말투 조사는 검색 그라운딩까지 켜는
무거운 요청인데 화면에서는 공짜로 보였습니다. 이제 `postGemini`가 직접 적습니다.

**둘. 도중에 멈춘 답변이 사라졌습니다.**
사용량은 스트림이 정상적으로 끝난 뒤에만 적었습니다. "눌러서 중지"로 멈추면
코루틴이 취소되면서 그 자리를 건너뛰었는데, 서버는 이미 입력을 다 읽은 뒤라
요금은 그대로 나갑니다. 이제 `finally`에서 적습니다. 사용량 조각이 하나도 못 온
경우에는 숫자를 지어내지 않고 **건수만** 남기고, 설정 화면에 그 건수를 밝힙니다.

**셋. 실패한 재시도가 세 배로 나갔습니다.**
어떤 실패든 조용히 두 번 더 보냈습니다. 키가 틀렸거나 요청이 잘못됐으면 몇 번을
보내도 똑같이 실패합니다. 이제 429와 5xx만 다시 보냅니다.

**넷. 캐시를 매 턴 새로 만들었습니다.**
답변을 받을 때마다 대화 접두사 전체를 새 캐시로 올리고 옛것을 지웠습니다.
한 턴 아끼자고 수만 토큰을 매번 다시 올린 셈입니다. 이제 새로 붙은 꼬리가
캐시의 5분의 1보다 커졌을 때만(또는 TTL이 4분 미만 남았을 때만) 다시 만듭니다.

**다섯. 메시지를 고치면 그 방이 캐시를 영영 잃었습니다.**
수정·삭제로 대화가 짧아지면 `usablePrefixCache`가 "덮는 턴이 더 많다"며 캐시를
안 쓰고 그냥 `null`을 돌려줬고, 갱신하는 쪽은 "이미 더 많이 덮는 캐시가 있다"며
그냥 돌아갔습니다. 그래서 그 방은 대화가 예전 길이를 되찾을 때까지 캐시 없이
전액을 내면서, 쓰지도 않는 캐시의 **보관료는 계속 냈습니다.** 이제 버리고
서버 쪽도 지웁니다.

**여섯. 캐시에 올린 토큰이 요금에 안 들어갔습니다.**
보관료만 적고 올린 토큰은 안 셌습니다. 캐시 생성 요청이 청구되는지 문서로
확인하지는 못했지만, 확실하지 않을 때는 비싼 쪽으로 잡습니다. `cacheCreateTokens`로
따로 세고 입력 단가로 더합니다.

**일곱. 검색 그라운딩이 쓴 입력이 빠졌습니다.**
`toolUsePromptTokenCount`를 안 셌습니다. 이제 입력에 더합니다.

### 고치지 않고 남겨 둔 것

- **사고 토큰.** `thinkingLevel`이 모드와 상관없이 늘 `medium`입니다. 사고 토큰은
  화면에 한 글자도 안 보이지만 출력 단가(입력의 5배)로 청구됩니다. 챗봇 모드의
  잡담에 medium이 필요한지는 의심스럽지만, 답변의 결이 이 앱의 핵심이라
  **사용자 판단 없이 낮추지 않았습니다.**
- **사진을 매 턴 다시 보내는 것.** 대화에 남아 있는 사진은 요청마다 다시 실립니다.
  긴 변 1600화소로 줄여 보내므로 한 장이 6타일 = 1,548토큰입니다. 캐시가 걸리면
  10분의 1 값이 되므로, 위의 캐시 수정으로 대부분 상쇄됩니다. 사진을 빼면 모델이
  "사진이 안 보인다"고 답할 수 있어 건드리지 않았습니다.
